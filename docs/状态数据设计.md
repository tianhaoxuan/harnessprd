# 状态机数据设计

> 版本 v0.1 ｜ 关联：`docs/状态机设计.md`（13 状态 / 40 转换）、`docs/对话阶段设计.md`（S0–S5）、
> `backend/core/questions_config.json`（20 题）、`backend/core/form_submission.schema.json`
>
> 前置决策：本期用**内存存储**（F7.1），Postgres 是 P1（F7.2）。因此本文把
> 「必须持久化」和「本期内存够用」分开标注，便于将来替换时不用重新讨论。

---

## 1. 三条设计原则

**① 单一真相。** 所有状态变更必须走同一个入口（§4.2 的 `apply_event`），
禁止任何代码直接改 `state` 字段。绕过入口的写入 = 绕过转换表和 guard 校验。

**② 内部状态与对外视图分离。** 内部 `SessionState` 可以自由增删字段；
对外 API 返回 `SessionSnapshot`（§4.3），字段只增不减。否则前端会被内部重构反复打断。

**③ 按会话自己的版本解释数据。** 会话记下创建时的 `form_version` 与 `prompt_version`，
读旧会话时按旧版本解释，不按当前配置 —— 否则改一次表单配置，历史会话就全乱了
（本项目的表单已经改过三次：v1.0 → v1.1 → v1.2，这不是假设）。

## 2. 数据契约

### 2.1 会话级

```python
SessionPhase = Literal[
    "created", "form_editing", "dialogue", "dialogue_summary",
    "prd_generating", "prd_review",
    "api_generating", "api_review",
    "prompts_generating", "prompts_review",
    "completed", "generation_failed", "abandoned",
]

DocKind = Literal["prd", "api", "prompts"]


class SessionState(BaseModel):
    # ---------- 标识 ----------
    id: str
    title: str | None                      # F1.6 会话自动命名；未命名时为 None

    # ---------- 状态机 ----------
    state: SessionPhase
    state_entered_at: datetime             # 进入当前状态的时间，供 F7.5 超时回收
    revision: int                          # 乐观锁，每次 save +1

    # ---------- 版本锚点 ----------
    form_version: str                      # 创建时的 questions_config.json 版本
    prompt_version: str                    # 生成时使用的提示词版本，用于追溯产物

    # ---------- 时间 ----------
    created_at: datetime
    updated_at: datetime

    # ---------- 各阶段数据 ----------
    form: dict[str, str]                   # 键 = 题目 id，值 = 作答（扁平，见 §3.1）
    form_submitted_at: datetime | None
    dialogue: DialogueState
    documents: dict[DocKind, DocumentState]

    # ---------- 异步任务与异常 ----------
    active_generation: GenerationTask | None
    failed_document: DocKind | None
    last_error: FailureInfo | None
```

### 2.2 对话数据

```python
class DialogueState(BaseModel):
    stage: Literal["S0", "S1", "S2", "S3", "S4", "S5"]
    round_index: int                       # F3.5 当前提问轮次
    max_rounds: int                        # 轮次上限（待定 4 或 5，见 S 系列待确认）
    stage_done: dict[str, bool]            # 每个阶段是否已完成
    active_turn: ActiveTurn | None         # 某一轮正在生成 AI 回复（见《会话持久化方案》§6）

    messages: list[Message]                # 完整对话历史
    pending_questions: list[PendingQuestion]   # 当前待用户回答的问题
    known_info: dict[str, Any]             # 已知信息（表单 + 各阶段结构化产出的合并结果）
                                           # ⚠️ 合并是硬性要求，见 §6.4
    open_questions: list[str]              # F3.6 跳过项 → PRD 第 8 章
    conflicts: list[Conflict]              # F3.11 发现的矛盾


class Message(BaseModel):
    id: str
    role: Literal["user", "ai"]
    stage: Literal["S0", "S1", "S2", "S3", "S4", "S5"]
    kind: Literal["say", "question", "answer", "summary"]
    content: str                           # AI 侧为 message 正文（Markdown）
    created_at: datetime


class PendingQuestion(BaseModel):
    """AI 提出的、等用户回答的问题。带建议答案是双向对话的前提。"""
    id: str
    question: str
    suggested_answer: str                  # 必填，对应提示词技巧 A2
    reason: str
    dimension: str | None                  # 对应 F3.8 的 5 个维度之一
    answered: bool = False


class Conflict(BaseModel):
    with_: str                             # 冲突来源：「表单 need_auth」/「S1 已确认的动线」
    detail: str
    raised_at: datetime
    resolved_at: datetime | None
    resolution: str | None


class ActiveTurn(BaseModel):
    """一轮对话的 AI 回复正在生成中。

    存在的意义是让「对话中刷新」可恢复：用户消息先落库、AI 回复后补，
    刷新后若最后一条是 user 且 active_turn 为空，即判定该轮未完成，服务端重新生成。
    详见《会话持久化方案》§6。
    """
    started_at: datetime
    stage: Literal["S0", "S1", "S2", "S3", "S4", "S5"]
```

### 2.3 文档数据

```python
DocStatus = Literal[
    "not_started", "generating", "pending_review", "approved", "stale", "failed"
]


class DocumentState(BaseModel):
    kind: DocKind
    status: DocStatus
    content: str | None                    # Markdown 正文
    version: int                           # 重生成次数，从 1 开始
    edited_by_user: bool                   # F4.12：改过就要在重生成前二次确认

    generated_at: datetime | None
    approved_at: datetime | None           # status 变 stale 后**保留**，用于显示"曾于 X 通过"
    updated_at: datetime

    stale_reason: str | None               # F4.9：为什么过期（如「PRD 于 X 修改」）
    feedback: str | None                   # F4.8：打回时用户给的反馈

    provider: str | None                   # 追溯：这次是哪家模型生成的
    model: str | None
    temperature: float | None
    usage: Usage | None                    # F4.13 token 用量
    checks: list[CheckResult]              # M8 质检结果


class Usage(BaseModel):
    prompt_tokens: int
    completion_tokens: int
    calls: int


class CheckResult(BaseModel):
    rule: str                              # 如 "F8.2 需求↔验收标准覆盖度"
    passed: bool
    detail: str


class GenerationTask(BaseModel):
    document: DocKind
    started_at: datetime
    attempt: int                           # 第几次尝试，失败重试时 +1
    cancel_requested: bool = False         # F4.10，进程内标志
    scope: Literal["full", "section"] = "full"   # F8.6：整份重生成 / 章节级重生成
    section: str | None = None             # scope="section" 时的目标章节标识


class FailureInfo(BaseModel):
    document: DocKind
    error: str
    at: datetime
    attempts: int
```

## 3. 每个状态需要保存哪些数据

「必须可读」= 渲染这个状态所需的最小集合，缺了就渲染不出来。

| 状态 | 必须可读 | 该状态会写入 |
| --- | --- | --- |
| `created` | `id`、`title`、`created_at`、`form_version` | `state`、`state_entered_at` |
| `form_editing` | `form_version`（决定渲染哪 20 题）、`form`（草稿） | `form`、`updated_at` |
| `dialogue` | `form`、`form_version`、`dialogue.*`（stage / round_index / active_turn / messages / pending_questions / known_info / open_questions / conflicts） | `messages`、`pending_questions`、`known_info`、`open_questions`、`conflicts`、`stage`、`round_index`、`stage_done`、`active_turn` |
| `dialogue_summary` | `dialogue.known_info`、`open_questions`、`conflicts` | 无（只读展示，仅接受确认事件） |
| `*_generating` | `active_generation`、`dialogue.known_info`（生成输入）、上游 `documents[kind].content` | `active_generation`、`documents[kind].status` |
| `*_review` | `documents[kind]`（content / status / checks / edited_by_user / version）、`dialogue.open_questions` | `documents[kind].status`、`content`、`edited_by_user`、`approved_at`、`feedback`、`stale_reason` |
| `completed` | 三份 `documents` 的 `content` / `status` / `approved_at`、`usage` | 无 |
| `generation_failed` | `failed_document`、`last_error`、`active_generation`（判断是哪一份失败） | `failed_document`、`last_error`（并清空 `active_generation`） |
| `abandoned` | `id`、`title`、`updated_at`（仅列表展示） | `state`，等待回收（F7.5） |

**三条推导规则**（不要重复存储）：

| 派生值 | 由什么推导 |
| --- | --- |
| `covered_dimensions`（F3.12 去重依据） | `form` 的非空项 + `questions_config[form_version]` 的 `covers_dimensions` + `dialogue.known_info` |
| 当前会话状态是否合法 | 转换表（`docs/状态机设计.md` §3.2） |
| 前端可用操作 `actions` | 当前 `state` 在转换表中的出边（§4.3） |

**对照会话状态与文档状态**：会话状态 = 第一份未 `approved` 的文档所处阶段。
因此 `documents` 的 `status` 是真相，会话的 `state` 是它的投影 —— 但**两者都要存**，
因为 `state` 还要表达 `form_editing` / `dialogue` 这些与文档无关的阶段。
写入时必须由 `apply_event` 同时更新，不允许只改一个。

## 4. 统一的状态数据接口

分四层，各司其职。

### 4.1 存储接口（唯一的数据出口）

```python
class SessionStore(Protocol):
    async def create(self, *, form_version: str, prompt_version: str) -> SessionState: ...

    async def get(self, session_id: str) -> SessionState | None: ...

    async def list(
        self, *, states: Sequence[SessionPhase] | None = None,
        limit: int = 20, cursor: str | None = None,
    ) -> tuple[list[SessionSummary], str | None]: ...

    async def save(self, state: SessionState, *, expected_revision: int) -> None:
        """乐观锁写入。expected_revision 与库中 revision 不符时抛
        ConcurrentModification，防止两个标签页互相覆盖。"""

    async def delete(self, session_id: str) -> None: ...

    async def reap(self, *, older_than: timedelta, states: Sequence[SessionPhase]) -> int:
        """F7.5 数据清理：回收长期停留的状态（created / abandoned / completed）。"""
```

两个实现：`InMemorySessionStore`（F7.1，本期）、`PostgresSessionStore`（F7.2）。
**业务代码只依赖这个 Protocol**，换实现不动上层。

### 4.2 状态转移入口（唯一的状态变更通道）

```python
async def apply_event(
    store: SessionStore, session_id: str, event: str, payload: dict, *,
    expected_revision: int | None = None,
) -> SessionState:
    """所有状态变更的唯一入口。步骤：

    1. 取会话（不存在 → SessionNotFound）
    2. 查转换表：当前 state 是否允许 event（不允许 → IllegalTransition）
    3. 校验 guard（如 submit_form 要求必填项通过 schema 校验）
    4. 执行副作用：
       - 回退到上游时，给下游 documents 标 stale + 写 stale_reason
       - 进入 *_generating 时创建 active_generation 并派发任务
       - 进入 generation_failed 时清空 active_generation
    5. 更新 state / state_entered_at / revision / updated_at
    6. 乐观锁写入
    """
```

**转换表和 guard 都必须在这里硬编码校验，不能只靠提示词或前端。**
前端的按钮显隐是体验问题，服务端的校验是正确性问题。

### 4.3 对外只读视图（API 契约）

```python
class SessionSnapshot(BaseModel):
    id: str
    title: str | None
    state: SessionPhase
    created_at: datetime
    updated_at: datetime

    # 进度：给进度条用，1–9 对应主流程九步
    step: int
    step_label: str

    form: dict[str, str]
    dialogue: DialogueView | None          # stage / round_index / pending_questions /
                                           # open_questions / conflicts（不含完整 messages）
    documents: dict[DocKind, DocumentView] # status / stale_reason / edited_by_user /
                                           # approved_at / version（不含 content）
    active_generation: GenerationView | None
    failure: FailureView | None

    # ⭐ 当前状态允许的操作，由转换表推导
    actions: list[str]


class DialogueView(BaseModel):
    messages: list[Message]                # 单独分页接口获取，快照里只带最近 N 条
    pending_questions: list[PendingQuestion]
    open_questions: list[str]
    conflicts: list[Conflict]
```

**`actions` 是这套设计的关键一环**：前端不自己判断"现在能不能点通过"，
而是直接用服务端给的动作列表渲染按钮。这样转换表（`docs/状态机设计.md` §3.2）
成为**唯一真相**，前端的按钮和状态机的规则不可能漂移。

**文档正文不进快照**：`content` 可能上万字符，快照每次都要拉会浪费。
单独提供 `GET /sessions/{id}/documents/{kind}` 取正文。

## 5. 持久化要求

### 5.1 必须持久化 —— 丢了会话就不可用

| 数据 | 为什么必须 |
| --- | --- |
| `id`、`title`、`created_at` | 会话的身份 |
| **`state`**、`state_entered_at` | **丢了刷新后无法恢复流程位置**，这是最核心的一条 |
| `revision` | 乐观锁；丢了并发写会互相覆盖 |
| **`form_version`**、`prompt_version` | 丢了无法正确解释 `form` 与追溯产物 |
| `form`、`form_submitted_at` | 用户填的东西，丢了要重填 |
| `dialogue.stage`、`round_index`、`stage_done` | 丢了对话要从头开始 |
| **`dialogue.messages`** | 丢了上下文断裂；AI 会重复问已答过的问题 |
| **`dialogue.active_turn`** | 不知道"某一轮正在生成 AI 回复"，刷新后该轮无法恢复（见《会话持久化方案》§6） |
| `dialogue.known_info` | 三份产物的唯一输入 |
| `dialogue.pending_questions` | 丢了刷新后用户不知道该答什么 |
| `dialogue.open_questions`、`conflicts` | 要写进 PRD 第 8 章 |
| `documents[*].status`、`content`、`version`、`edited_by_user`、`approved_at`、`stale_reason`、`feedback` | 产物本身；`edited_by_user` 丢了会静默覆盖用户的手工修改 |
| `active_generation.document`、`started_at`、`attempt` | 见 §6.1 孤儿生成态 |
| `failed_document`、`last_error` | 失败后要能显示原因并重试 |

### 5.2 建议持久化 —— 丢了影响追溯与体验

| 数据 | 影响 |
| --- | --- |
| `documents[*].usage` | F4.13 用量统计；丢了历史成本无法核算 |
| `documents[*].checks` | M8 质检结果；可重跑但要再花一次 LLM 调用 |
| `documents[*].provider` / `model` / `temperature` | 追溯「这份文档是谁生成的」 |
| `form_submitted_at`、`approved_at` 等各时间戳 | 审计与展示 |

### 5.3 不必持久化 —— 可重算或本就是进程内

| 数据 | 原因 |
| --- | --- |
| `covered_dimensions` | 由 `form` + `questions_config` + `known_info` 推导 |
| 表单校验结果 | 可重算，且必须按当前 schema 重算 |
| `active_generation.cancel_requested` | 进程内标志；进程重启后任务已不存在，标志无意义 |
| 生成任务的 asyncio 句柄 | 无法序列化，也不该序列化 |
| 前端渲染缓存、`step_label` 的文案 | 由配置/枚举推导 |

### 5.4 本期内存方案的实际后果

本期（F7.1）是内存存储，所以：

- **浏览器刷新不丢数据**（进程还在），F1.3 会话恢复可用
- **服务重启全丢** —— 所有会话消失，不存在"恢复"问题
- 因此 §6.1 的孤儿生成态**在内存方案下不会发生**，
  但**一旦切到 Postgres（F7.2）就必然发生**。实现 `PostgresSessionStore` 时必须同时实现它

## 6. 四个必须处理的边界

### 6.1 孤儿生成态（切 Postgres 后的头号 bug）

会话里 `state = prd_generating`，但生成任务已经不存在了（进程重启、任务崩溃、部署发版）。
不做处理的话，用户刷新后**永远停在"生成中"**，既不能取消也不能重试。

**恢复规则**（在 `get()` 返回前执行）：

```
若 state ∈ {prd,api,prompts}_generating：
    若 active_generation 对应的任务在本进程内活跃  → 正常，继续等待
    否则（判定为孤儿）→ 降级：
        state = generation_failed
        failed_document = active_generation.document
        last_error = { error: "生成任务已中断", at: now, attempts: attempt }
        清空 active_generation
```

降级而不是自动重试：生成有真实成本，不该在用户不知情时重复扣费。

### 6.2 表单版本漂移

会话的 `form_version` 与当前 `questions_config.json` 的版本可能不一致。规则：

| 情况 | 处理 |
| --- | --- |
| 一律 | **按会话的 `form_version` 解释 `form`**，不按当前配置 |
| 当前配置新增了题 | 在旧会话中视为「未作答」（即该维度未覆盖，对话可能需要补） |
| 当前配置删除了题 | 数据保留在 `form` 里，但**不参与** `known_info` 与生成 |
| 题目 `id` 被改名 | 视同「删除 + 新增」，需要迁移脚本或人工确认 |
| 主版本不兼容 | 提示「表单已更新，建议重新填写」，但不强制 |

> **由此推出一条配置变更纪律**：`questions_config.json` 的 `version` 必须遵循语义化版本 ——
> 新增题 = minor（1.2 → 1.3），删除题或改 `id` = **major**（1.2 → 2.0）。
> 现在的 v1.1 → v1.2 已经做过"新增 5 题"，属于 minor，规则成立。

### 6.3 对话历史增长

`messages` 会随轮次增长。本设计的提问轮次上限是 3–5 轮，正常体量很小，
但用户可以反复要求"回到前面补充"，理论上无上界。

规则：设硬上限（如 500 条），超出时把最早的部分折叠成一条摘要 `Message(kind="summary")`，
保留最近的完整消息。**不要静默丢弃** —— 用户会发现 AI"忘了"之前说过的内容。

### 6.4 阶段产出必须合并进 `known_info`（实测踩过的坑）

`apply_event` 在阶段推进时，必须把该阶段的**结构化产出**合并进 `dialogue.known_info`。
这不是"顺手做一下"的优化 —— 缺了它，生成阶段拿不到信息只能自己编。

端到端实测（`scripts/validate_prompts.py`）确认了缺失的后果：

| 缺失的产出 | 生成阶段的后果 |
| --- | --- |
| S1 主场景动线 | 第 6 章写不出场景，或自己编一个 |
| S2 功能边界 | 第 7 章边界条件退化成 `[待确认]` 或含糊表述 |
| **S3 优先级分级** | **第 7 章 7 条功能全部被标成 P0** |
| **S4 四组默认值**（成功指标 / 规模 / 硬约束 / 合规） | **合规小节被权限内容填满**（「仅第三方登录」「JWT 鉴权」「成员只能看自己的周报」—— 没有一条是合规要求） |
| S3 不做清单 | 第 5 章「本期明确不做」为空 |
| 跳过项 | 开放问题章为空 |

**为什么把 S4 单列出来**：它的四组默认值最容易漏。
S4 的产出是一段 message 正文加 3 个问题，**默认值本身不在 `questions` 里** ——
如果只合并"用户确认过的答案"，而没有把 S4 提出的默认值一并写入，
生成阶段就会以为合规维度是空的。

**落地要求**：

1. 每个阶段的产出定义一份**结构化摘要**（不是原始 message 文本）
2. `apply_event` 在 `info_sufficient` / 阶段完成时写入 `known_info`
3. S4 写入时，**未被用户明确否决的默认值一律视为已采纳**，来源标为「我替你定的」，
   供 S5 摘要的三分类使用

> 这条与提示词层的「禁止用邻近内容顶替缺失输入」是一体两面：
> 数据层保证信息送达，提示词层保证信息没到时不乱写。**只做一边都不够。**

## 7. 与既有文档的差异（需要同步）

设计过程中发现 `docs/功能清单.md` 附录 A 有两处与本设计冲突：

| 附录 A 现状 | 本设计 | 处理建议 |
| --- | --- | --- |
| Session 用 `status` | 用 `state` | 改名。`status` 与 Document 的 `status` 同名易混，且两者语义不同（会话阶段 vs 文档审核态） |
| Document 用 `stale` 布尔量 | 并入 `status` 枚举（`stale` 是其中一个取值） | 合并。会话状态要能推出「第一份未 approved 的文档」，若 `stale` 独立于 `status`，一份过期文档仍算 `approved`，推导会失效 |

另外附录 A 的 Session 字段缺少 `state_entered_at`、`revision`、`form_version`、
`prompt_version`、`stage`、`round_index`、`pending_questions`、`active_generation`、
`failed_document` —— 建议按本文 §2 重写附录 A。
