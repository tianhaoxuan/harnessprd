# 部署到服务器

> 目标读者：拿到这个仓库、要把它跑到一台 Linux 服务器上的人。
> 这份文档只讲**怎么跑起来**；`HANDOFF.md` 讲**这东西现在能做什么、不能做什么**。

## 0. 先说清楚：这个服务现在的形态（会直接影响你怎么部署）

| 事实 | 对部署的含义 |
| --- | --- |
| **没有用户体系**（`docs/技术栈.md` §3.3 明确不做） | **谁拿到地址谁就能用**，而每次生成都在烧你的 LLM 额度。上公网前必须自己加一层粗粒度保护（§5） |
| **服务端不存任何会话状态**：会话与三份产物都在**访问者自己的 localStorage** 里 | 服务是**无状态**的 → 可以随意重启、可以多副本；但换个浏览器/清缓存 = 什么都没有。**多用户之间不共享任何东西** |
| **生成是前台 SSE**，一次请求挂几十秒到几分钟（接口文档分 3 片 ≈ 90 秒） | 反代**必须关缓冲 + 放大读超时**，否则要么"不流式了"、要么 504。见 `deploy/nginx.conf` 的三条注释 |
| Postgres / Redis 在 compose 里，但**代码零依赖** | 起它们不会多出任何能力，**别为此多花精力**。要真持久化得先做会话层（F7.2） |
| 提示词、题目配置是**运行时读的文件**（`backend/core/prompts/*.md`、`questions_config.json`） | 部署时这些文件必须跟着走 —— 我们的镜像已经 `COPY . .` 全部带上 |

一句话：**本期是"单进程 + 静态前端 + 一个 LLM Key"的自用/内网形态**，部署本身很简单，
难的是**别把它当成多用户的线上服务**。

## 1. 最短路径（Docker Compose，推荐）

服务器上需要：Docker Engine 24+（含 compose v2）、能出网访问你的 LLM 供应商。

```bash
# 1) 把代码弄到服务器上 —— 两种情形，选一种
#
#    **本项目当前走 ②**：还没有远端仓库（连 .git 都没建），所以没有东西可 clone。
#
#    ① 有远端仓库时（升级就是 git pull）
#       git clone <你的仓库> harnessprd && cd harnessprd
#
#    ② 打一个包传过去（已在本机打好并核对过：`harnessprd.tar.gz`，372 KB，
#       110 个条目，含全部提示词文件、不含 backend/.env）
#       本机：scp harnessprd.tar.gz user@服务器:/tmp/
#       服务器：
#         mkdir -p ~/harnessprd && tar -xzf /tmp/harnessprd.tar.gz -C ~/harnessprd
#         cd ~/harnessprd
#
#       要自己重打（改了代码之后就这么做）——**注意排除本包自己**，否则会把上一版
#       嵌套进去（踩过：bsdtar 会把自己也扫进去）：
#         tar --exclude=.git --exclude=.venv --exclude=node_modules \
#             --exclude=validation_out --exclude=dist --exclude=__pycache__ \
#             --exclude=backend/.env --exclude=harnessprd.tar.gz \
#             -czf harnessprd.tar.gz .

# 2) 配密钥与配置 —— 这一步不做，compose 会直接报错退出（刻意的）
cp backend/.env.example backend/.env
#    至少改这三项：
#      DEFAULT_LLM_PROVIDER=deepseek
#      DEEPSEEK_API_KEY=sk-...
#      LLM_MAX_TOKENS=8192        ← 别调小，见 §5.1
#    CORS_ORIGINS 同源部署时其实用不上，但仍建议改成实际访问地址
#
#    ⚠️ **只改这几行，别把别处的 .env 模板整份贴进来**：本项目对**不认识的变量是静默忽略**的
#    （实测：填 ADMIN_TOKEN / DATA_DIR / TOKEN_BUDGET_MODE 那一套，应用照常启动、一个都不生效，
#    只有点"生成"时才发现全 503）。填完用 `smoke_check.py` 自查 —— 它会点名不认识变量与空 Key。

# 3) 上线前自查（**先跑这个**：忘了填 Key / 端口被占 / 容器出不了网，
#    都不会在 up 时报错，而是等用户点"生成"时才以"生成失败"暴露）
sh deploy/preflight.sh

# 4) 起应用（首次会构建镜像：后端装 Python 依赖，前端在容器里跑 pnpm build）
docker compose up -d --build api web

# 5) 起完再自检一次配置本身（离线、不联网、不花钱）
#    它会比对 .env 的变量名与代码里的配置字段，并检查当前 provider 的 Key 是否为空 ——
#    "填了别的项目的模板"这种错，只有这一条能抓到（见 §5.4）
docker compose exec api python scripts/smoke_check.py | tail -20

# 6) 看状态与日志
docker compose ps
docker compose logs -f api
```

对外访问：**`http://<服务器IP>:8080`**（端口由 `WEB_PORT` 覆盖）。

> ⚠️ **不要把 8000 端口暴露出去**：compose 里 `api` 用的是 `expose` 而不是 `ports`，
> 只有 nginx 能连到它。要本机调试后端再去 `docker-compose.yml` 里打开那两行注释。

### 为什么是 nginx 出静态、`/api` 反代

前端代码里**只写相对路径**（`/api/v1/...`，见 `frontend/src/services/api.ts` 的文件头注释），
开发期由 Vite 代理，生产期由 nginx 承担同一角色。所以：

- 浏览器看到的始终是**同源请求** → 没有跨域，不依赖 `CORS_ORIGINS`
- 前端镜像里**没有**后端地址，换域名不用重新构建

## 2. 裸机部署（不用 Docker）

适合"服务器上已经有 nginx、不想装 Docker"的情况。三个进程/角色：

```bash
# ---------- 后端 ----------
cd harnessprd/backend
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt        # 依赖的唯一来源
cp .env.example .env && vim .env                 # 同 §1 第 2 步
.venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8000 --timeout-keep-alive 75
```

用 systemd 托管（`/etc/systemd/system/harnessprd-api.service`）：

```ini
[Unit]
Description=harnessprd api
After=network-online.target

[Service]
WorkingDirectory=/opt/harnessprd/backend
# 密钥走 EnvironmentFile，不要写进 unit（unit 是 world-readable 的）
EnvironmentFile=/opt/harnessprd/backend/.env
ExecStart=/opt/harnessprd/backend/.venv/bin/python -m uvicorn main:app \
  --host 127.0.0.1 --port 8000 --timeout-keep-alive 75
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now harnessprd-api
curl -s localhost:8000/health | head -c 200      # 应返回 JSON
```

```bash
# ---------- 前端 ----------
cd harnessprd/frontend
corepack enable                # package.json 里固定了 pnpm@12.4.2
pnpm install --frozen-lockfile
pnpm build                     # = check:text && tsc --noEmit && vite build
sudo rsync -a --delete dist/ /var/www/harnessprd/
```

nginx：把 `deploy/nginx.conf` 拷进 `/etc/nginx/conf.d/harnessprd.conf`，
**把 `proxy_pass http://api:8000;` 改成 `http://127.0.0.1:8000;`**（裸机没有 compose 的服务名 DNS），
`root` 改成 `/var/www/harnessprd`，然后 `nginx -t && systemctl reload nginx`。

## 3. HTTPS

nginx（或它前面的云负载均衡 / Caddy）终止 TLS 即可，应用本身不关心协议：

```bash
sudo certbot --nginx -d prd.example.com
```

⚠️ 上 HTTPS 后记得把 `backend/.env` 的 `CORS_ORIGINS` 改成 `https://prd.example.com`
（同源部署下它用不上，但直连 API 调试时会用）。

## 4. 部署后必须做的验收（**别只看容器起来了**）

```bash
# ① 后端就绪 + Key 配上了（llm_configured 必须是 true）
curl -s http://<地址>/health

# ② 分片计划接口（不调模型，最快能确认"提示词文件跟上了"）
curl -s "http://<地址>/api/v1/conversation/document-plan?kind=api" | head -c 300
#    期望：multi_part=true，parts 是 3 片

# ③ 真跑一次生成（在浏览器里走完：填表 → 追问 → 生成 PRD → 生成接口文档）
```

**③ 的判据**（这一步能同时验证反代配置对不对）：

- 生成过程中文字是**逐段冒出来**的（不是憋一会儿整块蹦出来）→ 说明 `proxy_buffering off` 生效
- 接口文档页显示**「正在生成第 1/3 片 … 3/3 片」**并最终跑完 → 说明读超时够长、分片计划生效
- **页面上不该出现琥珀色的"没有生成完"警告** → 出现了说明输出仍被截断，去看 §5

如果日志里出现 `504`：是反代读超时；出现 `生成失败` 但后端日志正常：看浏览器控制台的响应。

## 5. 三个容易踩的坑

### 5.1 别把 `LLM_MAX_TOKENS` 调小

整份接口文档要 >10000 输出 token，8192 已经是**必须**的值（接口文档靠分片绕开这个限制，
分片预算是按这个上限算的）。调小会让每一片也开始被截断。

模型的上限就是 8192，**再往上调没用** —— 想让文档更完整只能改分片粒度（`services/document_plan.py`
里的 `_PART_BUDGET_CHARS`），不是调这个数。

### 5.2 反代配置里那三行不能省

`deploy/nginx.conf` 的 `proxy_buffering off` / `proxy_read_timeout 600s` /
`proxy_request_buffering off` 都是**功能性的**，不是调优：

- 关缓冲 → SSE 才是流式的（不关的话本地直连看不出问题，一挂反代就"变卡"）
- 读超时 → 一次生成几分钟，默认 60s 会 504
- 关请求缓冲 → 入参里有整份 PRD

### 5.3 加访问控制（**上公网前必须做**）
服务没有用户体系。最省事的三档，任选其一。

**① Basic Auth**（`deploy/nginx.conf` 里已备好三行注释，取消注释即可）：

```bash
# 生成密码文件。**注意：不要把明文密码交给在线工具**，下面这条纯本地生成。
# 大多数服务器没装 htpasswd，用容器跑一次最省事：
docker run --rm httpd:2.4-alpine htpasswd -nbB 你的用户名 '你的强密码' > deploy/.htpasswd

# 确认文件在且不是空的（.htpasswd 已加进 .gitignore，别提交）
wc -l deploy/.htpasswd

# 打开 deploy/nginx.conf，取消这三行的注释：
#   auth_basic "harnessprd";
#   auth_basic_user_file /etc/nginx/conf.d/.htpasswd;
#   （第三处：把 deploy/.htpasswd 也挂进 web 容器 —— 见下方 compose 片段）
sudo vi deploy/nginx.conf

# 让 web 容器能看到密码文件（docker-compose.yml 的 web.volumes 里追加一行）：
#   - ./deploy/.htpasswd:/etc/nginx/conf.d/.htpasswd:ro

docker compose up -d web          # 配置是挂载进去的，重建容器即可生效
# 验证：不带凭据应当 401，带上应当 200
curl -s -o /dev/null -w '%{http_code}\n' http://<地址>/health          # 期望 401
curl -s -o /dev/null -w '%{http_code}\n' -u 用户名:'密码' http://<地址>/health  # 期望 200
```

② 只在云安全组 / 防火墙里放行你自己的 IP（`deploy/nginx.conf` 里也留了 `allow/deny` 的位置）；
③ 放在 VPN / WireGuard 后面。

**这三种都能挡住"路人"，但挡不住"拿到密码的人"** —— 真要多人各用各的会话，
得先做服务端会话层（现在所有会话状态都在访问者自己的浏览器里，服务端什么都不知道）。

### 5.4 别把别处的 `.env` 模板整份贴进来（**静默失效**）

本项目对**不认识的变量是忽略**的（pydantic-settings 的默认行为，实测过）：把别的项目的模板
（`ADMIN_TOKEN`、`DATA_DIR`、`LOG_LLM_METRICS`、`CONTEXT_BUDGET_TOKENS`、`TOKEN_BUDGET_MODE`、
`TOKEN_ESTIMATOR`、`ANTHROPIC_BASE_URL` 那一套）填进 `backend/.env`，**应用照常启动，
而且一个都不生效**。表现是：页面能打开、表单能填，一点"生成"就失败（后端返回 **503**），
而 `/health` 里 `llm_configured` 是 `false`。

本项目的配置字段只有这些（`backend/core/config.py`，**.env.example 就是全量清单**）：

```ini
APP_NAME / VERSION / ENVIRONMENT / DEBUG / LOG_LEVELHOST / PORT / CORS_ORIGINS
DEFAULT_LLM_PROVIDER / DEFAULT_LLM_MODEL / LLM_TEMPERATURE / LLM_MAX_TOKENS / LLM_TIMEOUT
ANTHROPIC_API_KEY / OPENAI_API_KEY / DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / OPENAI_BASE_URL
POSTGRES_HOST / POSTGRES_PORT / POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB / REDIS_URL
```

自查（这一步就是为它加的）：

```bash
docker compose exec api python scripts/smoke_check.py | grep -E '\.env|Key'
# 会打印两行：
#   .env 里没有本项目不认识的变量名（不认识的名字会被静默忽略）  → 报出到底是哪几个变量
#   .env 里配了当前 provider（deepseek）的 Key                    → Key 空着会直接点名
```

另外两条同样静默的坑：

- **值后面不要写行内注释** —— `DEEPSEEK_API_KEY=sk-x  # 备注` 会把 `# 备注` 当成 Key 的一部分
- **`DEFAULT_LLM_MODEL` 留空**让代码按 provider 回退；**别填别的厂的模型名**（会把 `deepseek-chat` 发给 OpenAI，
  见 `HANDOFF.md` §4 坑 #17）

### 5.5 值也在被校验：写错会**启动即崩**

实测踩出来的第三种失败：变量名全对、Key 也填了，但**某个值不在允许集合里** —— 服务起来的瞬间
就抛 validation error 退出，容器进入 `Restarting (1)`，`docker compose ps` 显示 `api unhealthy`，
而日志里只有一行 pydantic 报错。最容易写错的两个：

| 变量 | 允许的取值 | 常见错法 |
| --- | --- | --- |
| `ENVIRONMENT` | `local` / `dev` / `staging` / `prod` | 写 `production`、`online`、`release` |
| `DEFAULT_LLM_PROVIDER` | `deepseek` / `openai` / `anthropic` | 写 `claude`、`gpt`；**大小写敏感** |

自查：

```bash
docker compose exec api python scripts/smoke_check.py | grep -E '\.env'
# 其中一行是「.env 里的值能被配置模型接受」，不合法时直接点名哪个字段错在哪
```

## 6. 升级与回滚

```bash
git pull
docker compose up -d --build api web      # 只重建有变化的镜像
docker compose logs -f api                 # 起来后看一遍日志
```

- **没有数据库迁移**（服务端不存状态），所以回滚就是 `git checkout <旧提交>` 再 `up -d --build`
- 升级后建议跑一遍离线自检（它不需要 Key、不联网）：
  ```bash
  docker compose exec api python scripts/smoke_check.py
  ```

## 7. 这个部署"还没有"的东西（别指望）

| 没有 | 什么时候会有 |
| --- | --- |
| 用户账号 / 权限 / 多租户 | 明确不做（`docs/技术栈.md` §3.3） |
| 服务端会话持久化（刷新/换设备还能接着用） | 要等会话层 `SessionStore`（F7.2）落地 |
| 生成的后台任务化（关页面不丢结果） | 见 `docs/会话持久化方案.md` §7.1；现在是前台 SSE，请求断了这一轮就没了 |
| 产物落库 / 分享链接 / 团队协作 | 同上，都要先有会话层 |
| 限流、审计、成本统计 | 没有；额度保护靠 §5.3 那一层 |
| 健康检查之外的监控指标 | 只有 `/health`（含 `llm_configured`） |

## 附：本地/内网快速自用（不开 Docker）

```powershell
# 后端
cd backend; .venv\Scripts\python -m uvicorn main:app --host 127.0.0.1 --port 8000
# 前端（另开一个终端）
cd frontend; pnpm dev          # http://127.0.0.1:5173
```

这条路径**不需要反代**（Vite 的 dev proxy 已经承担了），也是开发时的默认形态。
