### 3.1 三个漏项的根因

| 字段 | 表单里的描述 | 应该落在哪 | 为什么漏了 |
| --- | --- | --- | --- |
| `product_type` | 「决定 PRD 核心场景的写法与提示词套件的模块划分方式」 | PRD 第 6 章场景 + 套件类别 4 步骤划分 | 设计章节时按「信息维度」排，漏了「产品形态」这一维 |
| `platform` | 「决定接口文档的服务端范围与提示词套件的技术选型」 | PRD 第 11 章（端兼容性）+ 接口文档第 2 章（服务端范围）+ 套件类别 1（技术栈） | 被当成纯技术字段，只归给套件，但 PRD 也需要它写兼容性 |
| `style_preference` | 「只影响视觉与交互约定，不影响功能范围」 | 套件类别 1（UI 约定） | 被判定为「不影响功能」后**整条链路都没接住** |

> `style_preference` 最典型：字段定义里写着「不影响功能范围」，
> 设计模板时就没人管它 —— 但**不影响功能不等于不需要落点**。

| 信息 | 现状 | 判定 |
| --- | --- | --- |

| 端与兼容性（`platform`） | 无章节接 | 🔴 **漏** |
| 改造 / 迁移要求（`existing_system`） | 无章节接 | 🟡 **漏**（第 14 章只提「风险」，没有迁移要求本身） |
| 埋点与数据采集 | 第 9 章有「是否需要埋点采集第 3 章的指标」 | ✅ 已覆盖（`R6` 的关切已解决） |
| 视觉 / 交互风格 | 无章节接，且**本就不该进 PRD**（属实现约定） | ✅ 归套件，非 PRD 缺口 |

| 上线与灰度策略 | 无章节接 | 🟢 `hard_constraints` 只给时间约束，未要求发布策略 |

**结论：PRD 有 3 处缺口**（产品类型、端兼容性、迁移要求），
其中前两处直接源于 §3 的字段漏项。

## 5. 接口文档是否覆盖了所有功能

### 5.1 双向映射本身是完整的

| 方向 | 规则 | 位置 |
| --- | --- | --- |
| PRD 功能 → 接口 | 每条 P0 功能需求都应至少对应一个接口 | `gen_api.md` 质量要求 |
| 接口 → PRD 功能 | 每个接口必须有 `PRD 来源`（`FR-xx`） | 接口描述必填项第 4 项 |

### 5.2 但存在一处**规则冲突**

这两条放在一起会产生矛盾：

- 「PRD 每条的 P0 功能需求都应至少对应一个接口」
- 「不允许凭空造接口 —— PRD 里没有对应功能需求的接口就是多余的」

**纯前端功能**（界面交互、格式化展示、本地校验）不需要接口。
按第一条规则，模型会认为「这条 P0 没有接口 = 我漏了」，于是**造一个接口出来**。

而"是否存在纯前端功能"取决于 PRD 第 7 章怎么写 —— 完全可能发生。

**修法**：接口文档第 6 章「接口清单」增加一张**「无接口功能」表**：

| PRD 功能需求 | 为什么不需要接口 |
| --- | --- |
| FR-08 周报草稿本地暂存 | 浏览器 localStorage，无服务端交互 |

有了这张表，「覆盖」就是双向闭合的：每条 P0 要么出现在接口清单里，要么出现在无接口表里。

### 5.3 三类条件约定缺失

第 2 章「通用约定」目前覆盖了分页 / 鉴权 / 时间 / 金额 / 幂等 / 版本，
但以下三类在真实项目里很常见，**模板里没有位置放它们的约定**：

| 场景 | 需要的约定 | 触发条件 |
| --- | --- | --- |
| **入站回调（Webhook）** | 签名算法、重试策略、幂等键、来源 IP 白名单 | `integrations` 含支付 / 消息类服务 |
| **文件上传 / 下载** | `multipart/form-data`、大小上限、类型白名单、直传还是中转 | PRD 出现附件、头像、导出 |
| **实时接口** | SSE / WebSocket、心跳、断线重连、消息格式 | PRD 第 8 章出现实时要求 |

缺这三类不会**漏接口**，但会漏**接口的通用约定** —— 每个接口各写各的签名算法，就是灾难。

## 6. 提示词套件是否包含所有必要的指导类型

现有五类：总控 / 脚手架 / 数据层 / 功能实现 / 验收自检。

对照表单字段反查「某类信息有没有指导去处」：

| 信息 | 现状 | 判定 |
| --- | --- | --- |
| 技术栈与版本（`tech_stack`） | 类别 1 | ✅ |
| 目录结构、代码规范（`engineering_conventions`） | 类别 1 | ✅ |
| **视觉与交互风格（`style_preference`）** | **无** | 🔴 **无落点** |
| **安全与合规要求（`compliance`）** | **无**（PRD 第 11 章有，套件没有） | 🟡 **无落点** |
| **部署环境（`hard_constraints` 的一部分）** | 类别 2 有 Dockerfile / CI，但**没有部署与上线指导** | 🟡 **不完整** |
| 性能要求（`scale_expectation`） | 无专门位置 | 🟢 可进类别 1 的约束 |
| 模块划分（`product_type`、`page_count`） | 类别 4 的步骤划分 | ✅（但 `product_type` 无输入说明） |
| 数据约定、错误处理约定 | 类别 1 | ✅ |

**结论：套件缺 2 类指导**（UI / 样式约定、部署与上线），
另有 1 项（合规）需要补落点。

### 6.1 为什么不新增类别

套件是「五类」这个数字已经写进了 `docs/功能清单.md` §5.3 的对照关系里，
而且**类别数增加会让「一步一个可独立验收的模块」的粒度判断变模糊**。
因此这三项应当**并入现有类别**：

| 缺失项 | 并入 |
| --- | --- |
| UI / 样式约定 | 类别 1 总控（它是全局约定，且每步都要遵守） |
| 安全与合规约定 | 类别 1 总控（同上，属「不可协商的约束」） |
| 部署与上线 | 类别 2 脚手架（它本来就是环境类，且是一次性动作） |

## 7. 待确认项的处理情况

| 待确认项 | 三份模板是否处理 |
| --- | --- |
| Q1 OpenAPI 导出 | ✅ 接口文档 §6 已解耦（表格结构与 OpenAPI 字段一一对应） |
| Q5 目标工具 | ✅ 套件 §5.1 给了 Cursor / Claude Code / Codex / 通用四种形态 |
| **Q6 公司模板定制** | ❌ **未被任何模板处理** |

**Q6 的影响比看起来大**：如果答案是「需要公司模板定制」，
那么三份模板的**章节结构本身**就要变成可配置的 ——
现在三份模板都把章节清单**内嵌在生成 Prompt 里**（见 §8.3），
一旦章节可配，内嵌清单就必须改成运行时注入。
