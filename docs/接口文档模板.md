# 接口文档模板

> 版本 v0.1 ｜ 目标读者：**后端开发**（提供清晰的 API 设计）
> 关联：`docs/PRD模板.md`、`docs/功能清单.md` §5.2、`backend/core/prompts/clarify_s4.md`、`backend/core/questions_config.json`

## 0. 三条设计约束

**① 输入只有 PRD + 表单，每章必须有来源。**
和 PRD 一样，这份文档是自动生成的。没有输入来源的章节必然写成空话。

**② 与 PRD 的边界不能越。**

| 内容 | PRD | 接口文档 |
| --- | --- | --- |
| 实体有哪些、彼此什么关系 | ✅ 概述级 | 引用 |
| 字段类型 / 长度 / 必填 / 唯一 / 默认值 | ❌ | ✅ **字段级** |
| 功能做什么、边界条件是什么 | ✅ | 推导成接口与错误码 |
| 接口路径 / 方法 / 参数 / 响应 / 错误码 | ❌ | ✅ |
| 权限矩阵（谁能做什么） | ✅ | 推导成鉴权要求 |

**③ 设计原则必须随 `api_convention` 分支。**
表单里 `api_convention` 的取值决定了整份文档的形态 ——
选了「GraphQL」或「gRPC」，RESTful 那一套 URL 命名、HTTP 方法语义就完全不适用。
**模板的主干按 RESTful 写（默认路径），另在 §3.6 给出分支规则。**

## 1. 文档整体结构

| # | 章节 | 层级 | 写作风格 | 输入来源 | 字数预算 |
| --- | --- | --- | --- | --- | --- |
| 1 | 文档信息 | 必填 | 概要 | 系统自动 | ≤100 |
| 2 | 通用约定 | 必填 | 简洁 | `api_convention` + §4 默认值 | 300–600 |
| 3 | 鉴权与授权 | 条件 | 简洁 | `need_auth`、`api_convention`、PRD 第 4 章「技术规格」的认证与权限子块 | 200–400 |
| 4 | 数据模型 | 条件 | **详细** | PRD 第 4 章「技术规格」的数据与存储子块（实体清单）+ `core_entities` + S3 字段约束 | 600–2000 |
| 5 | 错误码表 | 必填 | 简洁 | §5 约定 + 各接口汇总 | 300–800 |
| 6 | 接口清单 | 必填 | 概要 | PRD 第 2 章「功能需求」的 MVP 表派生（按 `FR-xx` 标注来源） | 100–400 |
| 7 | 接口详情 | 必填 | **详细** | PRD 第 3 章「页面设计」的关键交互 + 第 2 章功能说明与边界条件 | 1500–5000 |
| 8 | 外部依赖 | 条件 | 简洁 | PRD 第 4 章「技术规格」的外部依赖子块 | 150–300 |
| 9 | 待确认 | 必填 | 简洁 | PRD 全文就地标注的 `[待确认]`（PRD 没有开放问题章） | 100–300 |
| 附 A | 枚举值汇总 | 条件 | 概要 | 数据模型派生 | ≤300 |
| 附 B | 变更记录 | 必填 | 概要 | 系统自动 | ≤100 |

**条件的触发规则**

| 章节 | 触发条件 | 不触发时 |
| --- | --- | --- |
| 3 鉴权与授权 | `need_auth` ≠ 「不需要：打开即用」 | 整章省略，§2 里注明「无鉴权」 |
| 4 数据模型 | `need_database` ≠ 「不需要」 | 整章省略，§2 里注明「无持久化」 |
| 8 外部依赖 | `integrations` 非空 | 整章省略 |
| 附 A 枚举值汇总 | 数据模型里存在状态字段或枚举字段 | 整个附录省略 |

> **为什么不把「数据模型」并进「接口详情」**：后端开发有两条独立的工作线 ——
> 先建表（要数据模型），再写接口（要接口详情）。合成一章会逼他们来回翻。

**总预算约 3250–10300 字。** 上限比 PRD（7300 字）还高，因为「接口详情」一章会随接口数量线性增长。
同样**远超 `llm_max_tokens = 4096`**，必须分章生成（与 `docs/PRD模板.md` §4.3 的结论一致）。

### 1.1 与 `docs/功能清单.md` §5.2 的对照

§5.2 给的结构建议是 6 项，本模板细化为 9 章 + 2 附录：

| §5.2 原建议 | 本模板 |
| --- | --- |
| 1 通用约定 | 第 2 章 + 第 3 章（鉴权独立） |
| 2 错误码表 | 第 5 章 |
| 3 数据模型 | 第 4 章 |
| 4 接口清单 | 第 6 章 |
| 5 逐接口详情 | 第 7 章 |
| 6 待确认 | 第 9 章 |
| — | 第 1 章 文档信息、第 8 章 外部依赖、附 A、附 B（新增） |

### 1.2 覆盖必须双向闭合（F8.3）

两条规则放在一起会冲突：

- 「PRD 每条 P0 功能需求都应至少对应一个接口」
- 「不允许凭空造接口 —— PRD 里没有对应功能需求的接口就是多余的」

**纯前端功能不需要接口**（界面交互、本地暂存、格式化展示）。
按第一条规则，模型会认为「这条 P0 没有接口 = 我漏了」，于是**造一个接口出来**。

**修法**：第 6 章「接口清单」必须同时输出**两张表**：

| 表 | 列 |
| --- | --- |
| 接口清单 | 方法 / 路径 / 用途 / 对应的 `FR-xx` |
| **无接口功能** | `FR-xx` / 功能名 / **为什么不需要接口** |

**判定规则**：PRD 第 2 章 MVP 表里的每条 P0 功能需求，
**要么出现在接口清单里，要么出现在无接口功能表里** —— 两边都不出现的才是真漏项。

无接口功能表的例子：

| PRD 功能需求 | 功能名 | 为什么不需要接口 |
| --- | --- | --- |
| FR-08 | 周报草稿本地暂存 | 浏览器 localStorage，无服务端交互 |
| FR-11 | 时间范围快捷选择 | 纯前端交互 |

### 1.3 互斥规则

每条 `FR-xx` **只能出现在两张表之一**：

| 情况 | 归入 |
| --- | --- |
| 该功能需要服务端接口 | 接口清单 |
| 该功能完全不需要服务端接口 | 无接口功能表 |

**不允许一条 FR 同时出现在两张表里。**

即使一个功能「整体需要接口、只有某个子能力不需要」，也**整条归入接口清单**，
并在接口详情的「业务规则」里说明该子能力由前端承担。

**为什么必须写成互斥**：这条规则是实测补上的。模型曾把 FR-03「人工修改周报草稿」
同时列进两张表 —— 无接口表里写「撤销未保存的修改是本地行为」，同一条又注明
「提交后的修改由 `PATCH /weekly-reports/{id}` 承载」。**撤销只是 FR-03 的子行为，不是 FR-03 整体。**
一旦允许这种写法，两张表都失去区分能力，「覆盖是否闭合」就再也无法机械校验。

## 2. 每个接口的描述格式

### 2.1 字段清单

**必填 8 项**

| 项 | 说明 |
| --- | --- |
| 接口名称 | 中文短名，如「生成周报草稿」 |
| 方法与路径 | `POST /api/v1/weekly-reports` |
| 用途 | 一句话说清做什么 |
| **PRD 来源** | 对应 PRD 的哪条功能需求（`FR-xx`）—— **这是 F8.3 跨文档一致性校验的依据，不可省** |
| 鉴权 | 是否需要登录 + 需要什么角色 |
| 请求参数 | 分三张表：路径参数 / 查询参数 / 请求体 |
| 响应 | 字段表 + **成功** JSON 示例 |
| 错误码 | 本接口可能返回的错误码清单（**引用**第 5 章的全局表，不重复定义） |

**条件 5 项**

| 项 | 何时必填 |
| --- | --- |
| 幂等性 | 写操作（POST / PUT / PATCH / DELETE）**必填** |
| 业务规则 | 该接口有特有校验或计算规则时 |
| 状态流转 | 操作会改变资源状态时（写清调用前 → 调用后） |
| 并发控制 | 存在多端同时修改可能时 |
| 关联验收标准 | 有对应 `AC-xx` 时（便于测试对照） |

**限流**不单独成项，统一写在第 2 章「通用约定」里，除非该接口有**特殊**限制。

### 2.2 完整示例

````markdown
### POST /api/v1/weekly-reports

| 项 | 内容 |
| --- | --- |
| 接口名称 | 生成周报草稿 |
| 用途 | 按指定群聊与时间范围生成一份周报草稿 |
| PRD 来源 | FR-02（按人 / 项目生成周报草稿） |
| 鉴权 | 需要登录；角色：团队成员及以上 |
| 幂等性 | 支持。客户端传 `Idempotency-Key` 请求头，相同 Key 在 24 小时内返回同一结果 |
| 状态流转 | 无（创建新资源，不改变已有资源状态） |

**路径参数**：无

**查询参数**：无

**请求体**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `chat_ids` | string[] | 是 | 群聊 ID 列表，1–5 个 |
| `range_start` | string | 是 | 起始时间，ISO 8601 UTC |
| `range_end` | string | 是 | 结束时间，ISO 8601 UTC，跨度 ≤ 31 天 |
| `group_by` | string | 否 | 分组方式，枚举 `person` / `project`，默认 `person` |

**请求示例**

```json
{
  "chat_ids": ["wx_chat_001"],
  "range_start": "2025-01-06T00:00:00Z",
  "range_end": "2025-01-12T23:59:59Z",
  "group_by": "person"
}
```

**响应 201 Created**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 周报 ID |
| `status` | string | 状态，枚举 `draft` / `published` / `archived` |
| `groups` | object[] | 分组结果 |
| `groups[].name` | string | 分组名（人名或项目名） |
| `groups[].items` | string[] | 该组的进展条目 |
| `created_at` | string | 创建时间，ISO 8601 UTC |

**响应示例**

```json
{
  "id": "rpt_7f3a2c91",
  "status": "draft",
  "groups": [
    { "name": "张三", "items": ["完成登录模块联调", "修复导出乱码"] }
  ],
  "created_at": "2025-01-13T02:15:00Z"
}
```

**错误响应**

| 错误码 | HTTP | 触发条件 |
| --- | --- | --- |
| `RPT001` | 422 | 时间跨度超过 31 天 |
| `RPT002` | 422 | `chat_ids` 超过 5 个 |
| `CHT001` | 403 | 无权访问指定群聊 |
| `AUTH001` | 401 | 未登录或令牌过期 |
| `EXT001` | 502 | 上游群聊服务不可用 |

**业务规则**

1. 生成的草稿按 `group_by` 分组，组内条目按消息时间正序
2. 过滤规则：少于 5 个字或纯表情的消息不进草稿
3. 时间跨度上限 31 天（防止拉取量过大）

**关联验收标准**：AC-01、AC-03
````

### 2.3 写接口的通用要求

所有会改变服务端状态的接口（POST / PUT / PATCH / DELETE）**必须**明确：

| 问题 | 必须回答 |
| --- | --- |
| 重复调用会怎样？ | 幂等性说明 + `Idempotency-Key` 用法 |
| 并发修改会怎样？ | 乐观锁字段（如 `version`）或 `If-Match` 头 |
| 失败时部分成功怎么办？ | 是整体回滚，还是返回部分成功的结果 |
| 是否会触发异步任务？ | 若是，返回 `202 Accepted` + 任务查询接口 |

## 3. 接口设计原则

### 3.1 URL 命名（RESTful）

| 规则 | ✅ | ❌ |
| --- | --- | --- |
| 用**名词复数**，不用动词 | `/weekly-reports` | `/getWeeklyReport` |
| 多词用 **kebab-case** | `/weekly-reports` | `/weekly_reports`、`/weeklyReports` |
| 资源层级**不超过两层** | `/teams/{id}/members` | `/teams/{id}/projects/{pid}/tasks/{tid}` |
| 资源 ID 放**路径**，过滤条件放**查询串** | `/reports/{id}`、`/reports?status=draft` | `/reports/status/draft` |
| 路径**不带版本以外的前缀** | `/api/v1/...` | `/api/v1/service/reports` |
| 子资源表达**归属**，不表达**操作** | `POST /reports/{id}/publish` | `POST /reports/{id}/doPublish` |

> 非 CRUD 的**动作型**操作（发布、归档、撤回）允许用 `POST /资源/{id}/动作名词`。
> 这是 REST 的常见妥协，比硬塞进 HTTP 方法更清晰。

### 3.2 HTTP 方法语义

| 方法 | 语义 | 幂等 | 安全 | 成功码 |
| --- | --- | --- | --- | --- |
| GET | 查询 | ✅ | ✅ | 200 |
| POST | 创建 / 动作 | ❌ | ❌ | 201 / 200 / 202 |
| PUT | **全量**替换 | ✅ | ❌ | 200 / 204 |
| PATCH | **局部**更新 | ❌ | ❌ | 200 / 204 |
| DELETE | 删除 | ✅ | ❌ | 204 |

**不要用 POST 做查询**（除非参数复杂到无法放进 URL —— 那种情况应重新设计资源）。

### 3.3 统一响应格式

**成功：直接返回资源，不套信封。**

```json
{ "id": "rpt_001", "status": "draft", "created_at": "2025-01-13T02:15:00Z" }
```

列表：

```json
{
  "items": [ { "id": "rpt_001" } ],
  "page": 1,
  "page_size": 20,
  "total": 137
}
```

**失败：统一错误体**（见 §4.2）。

**为什么成功不套 `{code, message, data}` 信封**：

- HTTP 状态码已经表达了成败，再套一层 `code: 0` 是冗余
- 信封会把所有字段下沉一层，前端解构和类型定义都变累赘
- 空响应（204）无法套信封

> 若团队已有统一信封规范，可以改 —— 但**必须全项目一致**，不能一半裸一半套。
> 这一条列入 §6 待确认。

### 3.4 命名与格式约定

| 项 | 约定 | 理由 |
| --- | --- | --- |
| JSON 字段命名 | **`snake_case`** | 与 Python / SQL 一致，后端主导时摩擦最小 |
| 例外 | 若 `tech_stack` 明确是 Node / TypeScript 主导，改 `camelCase` | 避免前端层层转换 |
| 时间 | **ISO 8601 + UTC**，如 `2025-01-13T02:15:00Z` | 不带时区的时间是 bug 源头 |
| 金额 | **整数分**（`int`），如 `1999` 表示 19.99 元 | 浮点数做金额必有精度问题 |
| 布尔 | `true` / `false`，不用 0/1 | |
| 空值 | 字段无值时返回 **`null`**，不省略字段 | **省略与 null 语义不同**：省略意为"不适用"，null 意为"有这个概念但当前无值" |
| ID | 字符串，带资源前缀，如 `rpt_7f3a2c91` | 前缀让日志和报错可读 |

### 3.5 分页、排序、过滤、幂等

| 项 | 约定 |
| --- | --- |
| 分页参数 | `page`（从 1 开始）+ `page_size`，默认 20，**上限 100** |
| 分页响应 | `items` / `page` / `page_size` / `total` |
| 排序 | `sort=field` 或 `sort=-field`（`-` 表降序），**白名单字段**，不在白名单直接 422 |
| 过滤 | 平铺查询参数，如 `?status=draft&chat_id=xxx` |
| 幂等 | 写操作支持 `Idempotency-Key` 请求头；相同 Key 在 24 小时内返回首次结果 |
| 版本 | 路径前缀 `/api/v1/`；破坏性变更才升版本，新增字段不升 |

> 分页上限、幂等窗口、版本策略这三项与 `clarify_s4.md` 已定下的默认值一致，不要各写各的。

### 3.6 非 RESTful 的分支规则

`api_convention` 选了别的风格时，§3.1–3.2 作废，按下列规则替换：

| `api_convention` | 替换 §3.1 / §3.2 为 | §3.3–3.5 仍适用 |
| --- | --- | --- |
| GraphQL | 单一入口 `POST /api/v1/graphql`；Query / Mutation 命名用 `动词 + 名词`；字段级错误放在 `errors` 数组里，**HTTP 一律 200** | 时间、金额、空值约定不变；分页改为 cursor 分页 |
| gRPC / RPC | 方法名 `Service.Method`；用 protobuf 定义请求响应；**无 URL 概念** | 时间用 `google.protobuf.Timestamp`、金额用整数分不变 |
| RESTful + Session / OAuth 2.0 | §3.1–3.2 不变，只改第 3 章鉴权 | 全部适用 |

**GraphQL 分支特别注意**：HTTP 状态码不再表达业务成败，因此 §4 的错误码约定要改成
「错误码放在 `errors[].extensions.code`」而不是 HTTP 状态码 + 响应体。

### 3.7 三类条件约定

第 2 章「通用约定」除了 §3.3–3.5 的通用项，还必须包含以下小节 ——
**只要触发条件成立就不能省**，否则每个接口会各写各的签名算法：

| 小节 | 触发条件 | 必须约定什么 |
| --- | --- | --- |
| **入站回调（Webhook）** | `integrations` 含支付 / 消息类服务 | 签名算法、重试策略与次数、幂等键、来源 IP 白名单、响应超时 |
| **文件上传 / 下载** | PRD 出现附件、头像、导入导出 | `multipart/form-data` 还是 Base64、大小上限、类型白名单、直传还是经服务端中转 |
| **实时接口** | PRD 第 5 章「非功能需求」或第 2 章功能说明里出现实时 / 推送要求 | SSE 还是 WebSocket、心跳间隔、断线重连策略、消息体格式 |

**只输出触发条件成立的**；不成立时整节省略，不要留空标题。

> 这三类不会导致**漏接口**，但会导致**漏通用约定** ——
> 结果是每个接口各写各的签名与重试逻辑，这是后期最难统一的一类技术债。

## 4. 错误码约定

### 4.1 错误码格式

```
{模块缩写}{3 位序号}
```

- **模块缩写**：3 个大写字母，取自 PRD 的实体或功能域（`USR` / `AUTH` / `RPT` / `CHT` / `EXT`）
- **序号**：3 位，从 `001` 开始；模块缩写 + 序号全局唯一

**序号分段建议**

| 区间 | 含义 |
| --- | --- |
| `001–099` | 参数与校验错误 |
| `100–199` | 鉴权与权限 |
| `200–299` | 业务规则冲突（如时间跨度超限） |
| `300–399` | 资源状态不允许（如已归档的周报不能编辑） |
| `900–999` | 系统与外部依赖 |

分段不是硬要求，但**同一模块内按此顺序分配**能让排查时一眼定位类别。

### 4.2 错误响应体

```json
{
  "code": "RPT001",
  "message": "时间范围不能超过 31 天",
  "details": [
    { "field": "range_end", "issue": "EXCEEDS_MAX_RANGE", "limit": 31 }
  ],
  "trace_id": "0af7651916cd43dd"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `code` | 是 | 业务错误码，全局唯一 |
| `message` | 是 | **给开发者定位问题的中文描述**，不是给终端用户的 UI 文案 |
| `details` | 否 | 字段级错误明细；参数校验失败时必填 |
| `trace_id` | 是 | 链路 ID，便于对着日志排查 |

**`message` 不面向终端用户** —— 用户看到什么文案由前端映射，
服务端不返回 UI 文案。这样改文案不需要发后端版本。

### 4.3 HTTP 状态码与业务码的关系

**HTTP 状态码表达"哪一类"，业务码表达"具体哪一种"。一个 HTTP 码可对应多个业务码。**

| HTTP | 何时用 | 典型业务码 |
| --- | --- | --- |
| 400 | 请求格式错误（JSON 解析失败等） | `GEN001` |
| 401 | 未登录 / 令牌过期 | `AUTH001` |
| 403 | 已登录但无权限 | `AUTH002`、`CHT001` |
| 404 | 资源不存在 | `RPT404` |
| 409 | 并发冲突 / 状态冲突 | `RPT301` |
| 422 | **参数合法但业务校验不过** | `RPT001`、`RPT002` |
| 429 | 触发限流 | `GEN429` |
| 500 | 服务端未预期错误 | `GEN500` |
| 502 / 503 | 外部依赖不可用 / 服务不可用 | `EXT001`、`GEN503` |

**400 与 422 的分界最容易搞错**：

- 400 = 请求本身就不合法（不是合法 JSON、缺 Content-Type）
- 422 = 请求合法，但值不满足业务规则（时间跨度超 31 天、群聊数超 5 个）

### 4.4 错误码表格式（第 5 章）

| 错误码 | HTTP | 含义 | 触发条件 | 处理建议 |
| --- | --- | --- | --- | --- |
| `AUTH001` | 401 | 未登录或令牌过期 | 未带令牌 / 令牌失效 | 跳转登录 |
| `RPT001` | 422 | 时间范围超限 | 跨度 > 31 天 | 提示用户缩小范围 |
| `RPT301` | 409 | 周报已归档 | 对 `archived` 状态的周报执行编辑 | 提示先恢复 |

**每个接口的「错误响应」小节只列出该接口可能触发的码，不重复写含义** ——
含义统一在第 5 章，避免两处描述漂移。

### 4.5 必须覆盖的错误

每个接口至少要考虑这几类，适用的必须出现在「错误响应」里：

| 类别 | 何时适用 |
| --- | --- |
| 参数校验失败 | 有请求参数 |
| 未登录 | `need_auth` ≠ 不需要 |
| 无权限 | 存在角色差异（PRD 第 4 章「技术规格」的认证与权限子块给了角色与可见范围） |
| 资源不存在 | 路径含资源 ID |
| 状态冲突 | 资源有状态字段 |
| 并发冲突 | 支持多端修改 |
| 外部依赖失败 | 该接口依赖外部服务 |

## 6. 关于 OpenAPI 导出（Q1）

`docs/功能清单.md` 的 Q1「是否同时产出 OpenAPI 3.1 YAML」尚未定。本模板**刻意设计成与该决策无关**：

- §2.1 的「路径 / 查询 / 请求体 / 响应」四张表，字段与 OpenAPI 的
  `parameters` / `requestBody` / `responses` 一一对应
- §4 的错误码表可机械映射到 `responses[].content.schema`
- §3.4 的命名与格式约定可写成 `components.schemas` 的公共约束

**因此 Q1 结论为"要"时，只需加一个转换器，不需要重新设计文档结构。**
唯一需要额外补的是 OpenAPI 必需的 `operationId`（可由「方法 + 路径」自动生成）。
