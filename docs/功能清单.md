## 1. 一句话定位

面向产品经理的文档生成工具：用户填一张表说明想做什么产品，AI 通过多轮对话补齐细节，
最后自动产出三份**互相咬合**的文档 —— PRD、接口文档、AI 提示词套件。

## 2. 目标用户与场景

| 角色 | 诉求 | 占比预期 |
| --- | --- | --- |
| 产品经理（主） | 从想法快速产出可评审的 PRD，并顺手把接口约定拉齐 | 高 |
| 独立开发者 / 创业者 | 一人多角色，需要 PRD + 接口 + 能直接喂给 AI 编码工具的提示词 | 中 |
| 研发 / 测试（次） | 消费产物，不主动使用工具 | 低 |

**核心场景**：从一句想法到「可评审、可开发、可交给 AI 编码工具执行」的文档包，
目标 10 分钟内完成，替代原本 2–3 天的文档工作。

**成功指标（可量化）**：三份文档一次生成的完整率 ≥ 90%；用户手动修改率 ≤ 20%；
从填表到产出全流程 ≤ 10 分钟。

## 3. 端到端主流程

```
① 新建会话
      ↓
② 填表单（20 题：base 13 + advanced 7）      → F2.1 / F2.2
      ↓
③ 多轮追问（AI 提问 → 用户作答 → 循环，直到信息足够）
      ↓
④ 信息摘要确认（用户点头或回去补）      → F3.9
      ↓
⑤ 串行生成三份文档（PRD → 接口文档 → 提示词套件）
      ↓
⑥ 查看 / 复制 / 下载 / 单份重生成
```

> 主流程图上每一步都必须能在功能清单里找到归属，否则流程和清单会各说各话。
> v0.1 的步骤④就是漏的，已在 v0.2 补为 F3.9。

### 关键设计判断：三份文档是链条，不是平行产物

| 产物 | 输入 | 依赖 |
| --- | --- | --- |
| PRD | 表单 + 对话 | 无（**唯一源头**） |
| 接口文档 | PRD 的功能需求 | 依赖 PRD |
| AI 提示词套件 | PRD + 接口文档 | 依赖前两者 |

因此生成必须**串行**，且上游改动后下游产物需要标记为"可能过期"（v0.1 只写了这句话，
没有对应功能点，v0.2 补为 F4.9）。这决定了生成编排器（F4.1）是必需组件，
而不是可以顺带写掉的循环。

### 模块职责边界

v0.1 有一处结构性问题：**「已知信息」（表单 + 全部问答汇总后的那份上下文）没有归属模块**。
它在附录 A 里以 `info_summary` 存在，被 M3 产生、被 M4 消费，却没有任何模块为它的组装、
去重、冲突处理负责——这类"人人都用、没人负责"的对象最容易在实现时变成一团散落的状态。
v0.2 通过 F3.9 / F3.11 / F3.12 把它归属到 M3。

其余边界规则：

| 边界 | 规则 |
| --- | --- |
| M2 ↔ M3 | 表单字段与追问维度高度重叠（目标用户、核心场景两边都会问）。规则：**表单已填的项不再追问**，靠配置里的 `covers_dimensions` 机械判定，见 F3.12 |
| M3 ↔ M4 | M3 只负责把信息问全、让用户确认（F3.9）；M4 只负责生成。**触发权在 M3 结束处交到 M4**，见 F3.10 |
| M4 ↔ M5 | M4 产出内容与状态，M5 只负责呈现；进度条属 M5，但状态由 M4 提供（F4.5） |
| M4 ↔ M8 | M4 负责生成，M8 **只校验不改写**；要改一律回到 M4 走重生成（F8.6） |
| M6 / M7 | 这两者是与其他模块不同层级的**支撑能力**（配置、存储），不是同级产品功能。编号保留以免打乱既有引用，但评审时不应与人并列讨论优先级 |

### M8 产物质检与一致性（v0.2 新增模块）

**为什么新增**：§5.1 写了「第 4 章每条功能需求都必须被第 6 章覆盖（**可自动校验**）」，
§5.3 要求提示词套件覆盖 PRD、§5.2 要求接口文档从 PRD 推导，但 v0.1 里**没有任何功能点承载这些校验**。
这类能力既不属于 M4（生成）也不属于 M5（查看），在原有模块划分下无处安放，因此独立成模块。
（逻辑上紧邻 M4 / M5；编号顺延为 M8，以免打乱既有引用。）

| 编号 | 功能点 | 优先级 | 状态 | 说明与验收要点 |
| --- | --- | --- | --- | --- |
| F8.1 | PRD 结构合规校验 | P1 | 缺失 | 八章齐全、功能需求条目含描述 / 输入 / 输出 / 边界。验收：不合格项逐条列出，而非整体判失败 |
| F8.2 | 需求 ↔ 验收标准覆盖度校验 | P1 | 缺失 | §5.1 明确要求的「可自动校验」。验收：报出第 4 章中未被第 6 章覆盖的条目编号 |
| F8.3 | 跨文档一致性校验 | P1 | 缺失 | 接口文档的每个接口都能追溯到 PRD 的功能需求，不凭空造接口。验收：报出无来源的接口 |
| F8.4 | 提示词套件完整性校验 | P2 | 缺失 | 套件步骤是否覆盖 PRD 全部 P0 功能 |
| F8.5 | 命名与术语一致性检查 | P2 | 缺失 | 同一实体在三份文档中命名一致（如「会话」不被写成「项目」） |
| F8.6 | 校验结果的修复入口 | P2 | 缺失 | 针对不合格项一键重生成对应章节。注意：修复动作回到 M4 执行，M8 自身不改写内容 |

> 质检全部落在 P1 / P2：按「没有它产品跑不起来」的口径，没有质检产品仍能出文档。
> 但本产品的价值几乎全在文档质量上，评审时可以把 F8.1–F8.3 视作事实上的 P0。

## 5. 三份产物的定义

三份产物的结构直接决定提示词怎么写，因此在这里固定下来。

### 5.1 PRD

- **读者**：产品 / 研发 / 测试 / 业务
- **表单输入**：`problem`（背景与问题）、`target_users`（目标用户）、`core_features`（功能需求）、`success_metrics`（成功指标）、`scale_expectation` + `compliance` + `hard_constraints`（非功能需求）
- **结构**：固定八章 —— 1 背景与问题、2 目标与成功指标、3 目标用户与核心场景、
  4 功能需求（P0/P1/P2 分级）、5 非功能需求、6 验收标准、7 风险与假设、8 开放问题
- **质量要求**：
  - 第 4 章每条含：描述、输入、输出、边界条件
  - 第 6 章用 Given / When / Then，逐条可测试
  - 第 4 章每条功能需求都必须被第 6 章覆盖 → **由 F8.2 承载校验**
  - 信息不足时不编造，写进第 8 章并就地标 `[待确认]`
- **硬规则**：只写需求本身，不写技术选型与实现细节

### 5.2 接口文档

- **读者**：前端 / 后端 / 测试；同时作为提示词套件的输入
- **表单输入**：`core_entities`（数据模型）、`api_convention` + `need_auth`（通用约定 / 鉴权）、`integrations`（外部依赖）、`scale_expectation`（分页与限流）
- **结构建议**：
  1. 通用约定（BaseURL、鉴权、Content-Type、时间与金额格式、分页、幂等）
  2. 错误码表（码、含义、触发条件、处理建议）
  3. 数据模型（实体与字段表：字段、类型、必填、说明）
  4. 接口清单（方法、路径、用途、鉴权）
  5. 逐接口详情（请求参数表、请求示例、响应字段表、响应示例、错误）
  6. 待确认
- **质量要求**：路径与字段命名全文一致；错误码全覆盖；示例 JSON 可直接粘贴使用
  → **由 F8.3 / F8.5 承载校验**
- **待确认**：是否同时产出 OpenAPI 3.1 YAML（Q1）

### 5.3 AI 提示词套件

- **读者**：用 Cursor / Claude Code 等工具的开发者
- **表单输入**：`tech_stack` + `engineering_conventions`（全局约定）、`page_count`（步骤粒度）、`existing_system`（新建 vs 改造）
- **定义**：把 PRD + 接口文档转成**按里程碑 / 模块拆分的分步实现提示词**，
  每步可直接整段粘贴执行
- **每步包含**：任务目标、前置上下文（依赖哪些已完成的步骤）、涉及的文件与接口、
  技术约束、验收点、禁止事项
- **形态**：`step-01 … step-N` 自包含步骤 + 一份「总控提示词」声明全局约定与代码规范
- **质量要求**：步骤之间无循环依赖；每步可独立验收；
  不重复粘贴整份 PRD，按需摘要引用以控制上下文长度 → **由 F8.4 承载校验**

## 6. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 单份文档生成 ≤ 90s；三份串行 ≤ 4min；单轮追问 ≤ 15s |
| 可靠性 | 单份失败不阻塞其余；失败可重试并可见原因；LLM 超时可配（现为 120s） |
| 成本 | 单会话 LLM 调用次数上限、`max_tokens` 上限（现为 4096）→ **计数与上限由 F4.13 承载**；表单输入长度上限由配置的 `maxLength` 承载（全部填满约 11450 字符） |
| 安全 | 无用户体系 → 默认仅本机 / 内网；API Key 只走环境变量、绝不进前端；配置接口严格白名单；生成的文档可能含商业信息，不做自动外发 |
| 可维护 | 提示词与表单定义均外置（`core/prompts/*.md`、`core/questions_config.json`）；保持 `api → services → core` 单向依赖，`services` 不 import `fastapi` |
| 兼容 | 中文为主；产物统一 Markdown；模型可换（不绑定单一厂商） |
