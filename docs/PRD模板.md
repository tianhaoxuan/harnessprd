## 0. 三条设计约束

这份 PRD 是**自动生成的**，不是人写的。这个前提决定了模板的形态：

**① 每一章都必须有明确的输入来源。**
生成它的输入只有两处：20 题表单（`backend/core/questions_config.json`）+ 对话产出（S0–S5）。
**没有输入来源的章节一定会被写成空话** —— 这是自动生成文档最大的失败模式。
所以模板给每章都标注了「输入来源」，无来源的章节不进模板。

**② 章节分三层：必填 / 条件 / 附录。**

| 层级 | 含义 |
| --- | --- |
| **必填** | 任何项目都要有 |
| **条件** | 满足触发条件才生成，不满足则**整章省略**（不是留空标题） |
| **附录** | 派生或系统自动填充，不占正文篇幅 |

**③ 与两份下游文档划清边界。** PRD 只写"做什么、为什么、什么算做对"，
不写"接口长什么样"（那是接口文档）、不写"代码怎么组织"（那是提示词套件）。
边界写错会导致同一份内容在三处重复且互相矛盾。

| 内容 | PRD | 接口文档 | 提示词套件 |
| --- | --- | --- | --- |
| 背景、目标、用户、范围 | ✅ | — | 摘要引用 |
| 功能行为、业务规则 | ✅ | 推导接口 | 推导实现步骤 |
| 核心实体与关系 | ✅ **概述级** | ✅ **字段级** | 引用 |
| 接口路径、字段类型、错误码 | ❌ | ✅ | 引用 |
| 目录结构、代码规范、依赖选择 | ❌ | — | ✅ |

**风格三档的定义**

| 风格 | 含义 | 反面 |
| --- | --- | --- |
| **概要** | 3–5 行或一张表，只给结论，不写论证 | 展开成段落 |
| **简洁** | 一段话或一张表，要点齐全但不展开 | 写成多个子节 |

实现时必须调整（见 §4.3）。

## 2. 各章详述

### 第 1 章 文档信息

- **风格**：概要，一张表
- **内容要点**：产品名称、文档版本、生成时间、生成模型、**对应的表单版本**、文档状态（草稿 / 已评审）
- **不要写**：目录、修订历史（那在附 B）
- **作用**：这是自动生成文档的**溯源信息**。读者要能判断"这份 PRD 是基于哪一版表单生成的"

### 第 2 章 背景与问题

- **风格**：简洁
- **内容要点**：
  1. 现状：现在用户是怎么做的（`problem` + S1 的现状追问）
  2. 痛点：这么做的问题是什么，**能量化就量化**（"一次要花两小时"）
  3. 不解决的后果
- **不要写**：解决方案（那是第 7 章）、市场分析、竞品（本期不做且无输入来源）
- **反例**：❌「随着业务发展，效率问题日益突出」—— 无信息量，任何产品都适用

### 第 3 章 目标与成功指标

- **风格**：简洁，**指标必须用表格**
- **内容要点**：

  | 指标 | 当前值 | 目标值 | 期限 | 测量方式 |
  | --- | --- | --- | --- | --- |

  至少一条指标要对应"有人用"（用户量 / 留存），至少一条对应"真的有用"（效率 / 质量提升）
- **不要写**：无法量化的目标（"提升体验"）
- **注意**：「测量方式」这一列容易被漏。如果指标要靠系统埋点采集，**要在第 9 章的数据需求里体现出来**

### 第 4 章 目标用户与角色

- **风格**：简洁，角色用列表或表格
- **内容要点**：每类角色的**特征**（不是人名的堆砌）与**核心诉求**；如果只有一类角色，明确写"单角色产品"
- **不要写**：用户画像的细节描写（年龄、爱好），除非它直接影响功能
- **注意**：本章只回答"有哪几类人"，**"每类人能做什么"在第 10 章**

### 第 5 章 范围边界

- **风格**：简洁，**必须用两张表：做 / 不做**
- **内容要点**：

  | 本期做 | 说明 |
  | --- | --- |

  | 本期明确不做 | 原因 |
  | --- | --- |

- **不要写**：模糊的"后续可考虑" —— 要么进"不做"，要么进第 15 章开放问题
- **作用**：**这是开发最需要的一章。** 没有"不做清单"，需求会在开发过程中持续膨胀

### 第 6 章 核心场景与用户动线

- **风格**：**详细**
- **内容要点**：1–3 条主场景，每条写成**编号步骤的完整动线**，覆盖：触发时机 → 用户操作 → 系统响应（含等待时长）→ 产出 → 后续动作
- **输入**：对话产出的主场景动线（S1）+ **`product_type`** —— 产品类型决定场景怎么写：工具类写单点操作，平台类写多方协作，管理系统写角色间的流转
- **不要写**：异常分支和边界（那是第 8 章）、界面细节
- **反例**：❌「用户可以方便地生成周报」—— 这不是动线，是愿望

### 第 7 章 功能需求（**核心章节**）

- **风格**：**详细**
- **内容要点**：按 **P0 / P1 / P2** 分级；**每条功能独立成节**，且必须含五项：

  | 项 | 要求 |
  | --- | --- |
  | 描述 | 一句话说清做什么 |
  | 输入 | 从哪来、什么格式、必填与否 |
  | 输出 | 产出什么、什么形态 |
  | 边界条件 | 空数据 / 失败 / 超量 / 权限 / 重复 / 撤销 + 时间与时区 / 并发 / 一致性 / 授权撤销 / 精度 / 版本（12 类，见对话阶段设计 §S2） |
  | 优先级 | P0 / P1 / P2，并说明**为什么**是这个级别 |

- **不要写**：技术实现（用什么框架、什么算法）、接口路径、数据库表结构
- **P0 的定义**：没有它产品跑不起来。P0 超过 5 条就说明范围失控
- **硬要求**：**本章每一条都必须能被第 13 章覆盖**（由 F8.2 自动校验）

### 第 8 章 业务规则与状态流转

- **风格**：**详细**
- **内容要点**：状态机图或状态表（状态 / 触发事件 / 目标状态 / 条件）；跨功能的业务规则；计算规则与优先级规则
- **不要写**：单个功能内部的边界（那些写在第 7 章对应功能的"边界条件"里）
- **触发条件**：S3 挖到了状态流转或跨功能规则才生成

### 第 9 章 数据需求概述

- **风格**：简洁
- **内容要点**：核心实体清单（名称 + 一句话职责）、实体间关系（一对多 / 多对多）、**数据保留期限**、是否需要埋点采集第 3 章的指标
- **条件子节「迁移要求」**：当 `existing_system` = 「需要迁移历史数据」时**必须增补** —— 迁移的数据范围、数据质量要求、迁移窗口、失败回滚方式
- **不要写**：**字段级的类型、长度、索引** —— 那是接口文档「数据模型」章的职责
- **边界**：本章回答"系统里有哪些东西"，接口文档回答"每个东西长什么样"
- **触发条件**：`need_database` ≠ 「不需要」

### 第 10 章 权限与角色矩阵

- **风格**：简洁，**用矩阵表**
- **内容要点**：

  | 能力 \ 角色 | 角色 A | 角色 B | 未登录 |
  | --- | --- | --- | --- |

  标注可见性（能看什么）与操作权（能改什么）两个维度
- **不要写**：鉴权的技术方案（JWT / Session），那是接口文档
- **触发条件**：`need_auth` ≠ 「不需要：打开即用」

### 第 11 章 非功能需求

- **风格**：简洁，**逐条可验证**
- **内容要点**：性能（响应时间 / 并发）、可靠性（可用性 / 失败行为）、安全（加密 / 审计）、合规（数据出境 / 个人信息）、可维护性
- **输入**：`scale_expectation`、`compliance`、`hard_constraints` + **`platform`** —— 端形态决定**兼容性要求**（支持的浏览器与版本、是否需要响应式、移动端适配范围）
- **不要写**：无法验证的表述（"系统应稳定可靠"）
- **反例**：❌「系统应保证高性能」 ✅「列表接口 P95 响应时间 ≤ 500ms」

### 第 12 章 依赖与外部集成

- **风格**：简洁
- **内容要点**：每个外部服务一行 —— 服务名、用途、**凭证获取方式**、**配额或计费**、不可用时的降级行为
- **不要写**：集成的技术实现、SDK 选择
- **触发条件**：`integrations` 非空
- **注意**：「凭证获取方式」是 S0 难点判断的落点，也是这类项目最常见的阻塞点

### 第 13 章 验收标准

- **风格**：**详细**，**必须用 Given / When / Then**
- **内容要点**：逐条对应第 7 章的功能；包含正常路径与关键异常路径；每条可被测试
- **不要写**：无法执行的验收项（"用户满意度达到 90%"）
- **硬要求**：**覆盖第 7 章的全部条目**（F8.2 校验）。未被覆盖的功能需求就是没验收标准的开发任务
- **格式**：

  ```
  AC-01（对应 FR-03）
  Given 已登录用户位于周报列表页
  When  点击「生成周报」并选择时间范围
  Then  30 秒内展示草稿，且草稿按人分组
  ```

### 第 14 章 风险与假设

- **风格**：简洁
- **内容要点**：风险（描述 + 影响 + 缓解措施）、假设（**明确列出所有"我们假定成立"的前提**）
- **不要写**：泛泛的风险（"需求可能变化"）
- **注意**：S0 的难点判断（外部依赖的凭证、配额）应当落在本章
- **输入补充**：`existing_system` ≠ 「全新项目」时，必须补一条**改造 / 迁移风险** ——
  影响哪些已有功能、旧数据或旧接口的兼容边界在哪、改造期间能否与旧系统并行

### 第 15 章 开放问题

- **风格**：简洁，用列表
- **内容要点**：每条包含 —— 问题、**为什么现在没定**、影响范围、建议的决策时间点
- **不要写**：已经决定的事；也不要为了"看起来完整"而隐藏未决项
- **来源**：对话中用户跳过的项（`open_questions`）+ 全文各处标注的 `[待确认]` 汇总
- **作用**：本章是正式内容，不是缺陷清单

### 附录 A 术语表

- **风格**：概要，**用表格**（术语 / 英文 / 定义）
- **内容要点**：全文出现的业务术语与自造词
- **作用**：防止同一个概念在 PRD、接口文档、代码里出现三种叫法

### 附录 B 变更记录

- **风格**：概要
- **内容要点**：版本 / 日期 / 变更内容 / 触发原因（如"用户在第 3 轮对话中修改了需求"）

### 4.3 关于 `llm_max_tokens` 的提醒

这是最容易被忽略的一条：**按本模板生成的完整 PRD 需要多少输出 token？**
早先的估计是"现配置 4096 装不下"（`LLM_MAX_TOKENS` 已提到 **8192**）。实测结果见本节末尾：
**整份 PRD 只用了约 4000 token，8192 够用**；撞上限的是另外两份产物。
两个选择：

| 方案 | 说明 |
| --- | --- |
| 提高 `max_tokens` 到 8192+ | 简单，但一次生成时间长、失败后全部重来 |
| **分章生成**（推荐） | 先出第 1–5 章（概要部分），再分批出第 6–7 章、第 13 章，最后拼装。失败可只重跑某批 |

分章生成还有个额外好处：**它天然支持 F8.6「重生成对应章节」**。

**实测补充（真机端到端跑通后）**：按本模板整份生成，实测产出了 **15 章 + 2 附录齐全、
无占位符残留**的完整 PRD，共 **6723 字符 ≈ 4000 输出 token** —— 只占 `LLM_MAX_TOKENS=8192`
的一半。也就是说上面「约 9000–10000 输出 token」的估算**偏悲观**，8192 装得下完整结构
（这与「整份生成会撞上限被截断」的担心相反，实测未截断）。

但代价是**每章被压薄**：平均约 400 字，主要是表格（全文 98 行表格），
第 7 章的功能需求靠 6 条 FR 承载。所以「分章生成」的理由应从
「**装不下**」改为「**写得深**」（顺带支持 F8.6 单章重生成）。

证据：`backend/validation_out/flow_prd.txt`；耗时见 `HANDOFF.md` §2 的性能条目。

> **后续实测（同一轮端到端）**：真正撞上限的是**接口文档与提示词套件** ——
> 整份接口文档实测 17257 字符（≈10100 输出 token）、套件 18354 字符，**都在半途被切断**
> （`finish_reason=length`，页面会给出截断警告）。所以本节 R4「提高 max_tokens 还是分章生成」
> 的答案已经明确：**`max_tokens` 提到 8192 就到头了（厂商上限），第二、三份产物必须分片**；
> 见 `HANDOFF.md` §4 坑 #18、§6 第 8 项。
>
> ✅ **已实现**（`HANDOFF.md` §4 坑 #20）：分片计划由 `services/document_plan.py`
> **从本项目的提示词文件里解析**（接口文档取 `gen_api.md` 的章节清单表并按字数上限分批），
> 经 `GET /conversation/document-plan` 下发，前端逐片调用再拼接。实测结果：
> 接口文档 **3 片 → 20126 字符、1–9 章 + 附录 A/B 齐全、任一片都没截断**；
> 套件 **3 片 → 32949 字符、12 个文件块、无截断**。留档 `validation_out/split_*.txt`。
> **所以"分章生成"这个建议在这两份产物上已经从"建议"变成了运行时的默认行为。**
