# AI 对话阶段设计

> 版本 v0.1 ｜ 关联：`docs/功能清单.md` 的 M3（F3.1–F3.15）、§5 三份产物定义
>
> 本文只设计**表单提交之后、文档生成之前**这段对话。表单本身见 `backend/core/questions_config.json`。

---

## 1. 设计前提

### 1.1 对话不需要重复问表单已经拿到的东西

表单 20 题已经覆盖了 F3.8 的 5 个追问维度，且每个问题都用 `covers_dimensions` 声明了它答的是哪一个。
所以**对话的起点不是空白**：凡是「已填写且非空」的维度，一律不再问（F3.12）。

只有两种情况会让某个维度重新变成话题：

| 情况 | 例子 |
| --- | --- |
| 选填题留空 | `success_metrics`（成功指标）是选填，用户没填 → S4 必须补 |
| 答案过粗，不足以支撑产物 | `core_features` 填了「生成周报」，但 PRD 第 4 章要求每条功能含输入 / 输出 / 边界条件 → S2 必须细化 |

第二种是本设计的关键：**对话的价值不在于"问更多"，而在于把粗答案磨成可开发的粒度。**

### 1.2 对话的唯一职责

| 产物章节 | 表单给了什么 | 对话要补什么 |
| --- | --- | --- |
| PRD 第 3 章 目标用户与核心场景 | 角色（`target_users`） | **完整动线**：谁、什么时候、按什么步骤、拿到什么 |
| PRD 第 4 章 功能需求 | 3–5 条一句话功能 | **输入 / 输出 / 边界条件 + P0/P1/P2 分级** |
| PRD 第 5 章 非功能需求 | 规模、合规、硬约束（**均为选填**） | 留空时补默认值并让用户确认 |
| PRD 第 6 章 验收标准 | 无 | **什么算做对了**（对话给口径，产物写成 Given/When/Then） |
| PRD 第 8 章 开放问题 | 无 | 跳过 / 未决项的收集（F3.6） |
| 接口文档 数据模型 | 实体与字段（**选填**，且通常很粗） | 字段级约束：类型 / 必填 / 唯一 / 默认 / 状态枚举 / 级联 |
| 接口文档 通用约定 | **无字段覆盖** | 分页 / 错误码 / 版本 / 幂等 / 时间与金额格式 —— **只能约定，无法从功能推导** |
| 提示词套件 模块拆分 | 页面数、技术栈、工程约定（**均选填**） | 实现顺序与模块边界 |

### 1.3 时间预算

§2 定的成功指标是「从填表到产出全流程 ≤ 10 分钟」。据此反推：**对话部分最多 3–5 个提问轮次**（与 F3.5 一致），因此每个阶段必须能条件跳过，不能是固定全跑一遍。

## 2. 双向对话的响应结构（核心机制）

F3.8 只要求「问得准」，但你要的是**双向**——AI 给建议而不只是追问。落到提示词层面，
就是规定 AI 每一轮的输出必须包含这四段，缺一不可：

```
【我的判断】  基于已知信息，我倾向怎么做 / 我认为难点在哪
【依据】      为什么这么判断（一句话，不要长篇）
【我的建议】  一个具体的默认答案，用户可以一键采纳
【需要确认】  1–3 个问题，每个都挂着我建议的答案
```

### 举例：同一个问题的单向 vs 双向

| 模式 | AI 的说法 |
| --- | --- |
| ❌ 单向追问 | 「周报需要支持哪些导出格式？」 |
| ✅ 双向对话 | 「导出这块我建议**只做 Markdown 和飞书文档**，理由是你的目标用户是技术负责人，Markdown 能直接贴进周报群，而 PDF 排版成本高、周报场景几乎用不上。如果你们公司强制用钉钉，告诉我，我换成钉钉文档。」 |

### 三条硬规则

1. **不空问**：每个问题必须附一个具体建议，用户可以直接说「就按你说的」。
2. **不重复问**：表单已答、历史已答的内容一律不再问（F3.12）。问之前先查 `covers_dimensions` 与已答记录。
3. **不静默覆盖**：对话答案与表单答案冲突时**必须显式指出**（F3.11），不能默默以新答案为准。

冲突处理的例子：

> 「等一下，这里和你表单里填的对不上：`need_auth` 你选的是「不需要：打开即用」，但刚才说要**按人看自己的周报**。按人看就必须知道你是谁。是我理解错了，还是你想改成要登录？我建议改成「需要：仅第三方登录」，因为你成员本来就在企业微信里。」

### 关于「一键采纳」

建议答案要能被一键采纳，这是双向模式能压缩时间的关键——用户只需判断，不需要从零描述。落到数据上，
每一轮的 AI 输出除了文本，还应携带结构化的问题列表（`question` + `suggested_answer`），
前端才能渲染出「采纳 / 我自己填 / 跳过」三个按钮。这一点现有 `clarify.md` 的纯文本输出做不到。

## 3. 阶段总览

| 阶段 | 名称 | 话题 | 目标 | 触发条件 | 提问轮次 | 对应 Prompt |
| --- | --- | --- | --- | --- | --- | --- |
| **S0** | 开场复盘 | 我对你表单的理解 | 让用户确认方向、暴露分歧 | 总是 | 0（不计轮次） | `clarify_s0.md` |
| **S1** | 场景落地 | 用户动线 | 得到至少一个完整、可复述的使用场景 | 总是 | 1 | `clarify_s1.md` |
| **S2** | 功能细化 | 功能的输入 / 输出 / 边界 / 异常 / 字段级约束 | 每个 P0 功能都能直接开发 | 总是 | 1–2 | `clarify_s2.md` |
| **S3** | 边界与优先级 | 做什么、不做什么、先做什么 | 范围收敛 + P0/P1/P2 分级 | 总是 | 1 | `clarify_s3.md` |
| **S4** | 约束、接口约定与验收 | 非功能、接口通用约定、什么算做对 | 补齐空维度 + 澄清粗答案 + 定下可测试的验收口径 | 上述字段任一为空，**或存在「填了但很粗」的字段** | 1 | `clarify_s4.md` |
| **S5** | 摘要确认 | 信息汇总 | 用户确认，交接生成 | 总是 | 0（不提问） | `clarify_s5.md` |

提问轮次合计 **3–5 轮**，与 F3.5 的上限一致。S0 与 S5 不计入轮次——它们不产生新信息，只做对齐与收口。

### 阶段由谁决定

**阶段状态由服务端持有，作为参数注入提示词，不让模型自己判断现在处于哪个阶段。**
理由：模型自判阶段不可测、易漂移（同一份输入两次可能落在不同阶段），而阶段错了整个追问方向就错了。
服务层根据「已覆盖维度 + 当前轮次」推进阶段，模型只负责在给定阶段内把话说好。

## 4. 各阶段详述

### S0 开场复盘

- **核心任务**：把表单读回来，用一段话复述「我理解你要做什么」，并给出**难点判断**。目的是让用户在投入 5 分钟问答之前先纠正方向。
- **话题**：AI 对这份需求的理解，以及打算问什么。
- **产出**：用户对理解方向的确认或修正。

**话术示例**

> 「我看了你的表单，先复述一遍确认没跑偏：
>
> 你要做一个 **Web 端的群聊周报助手**，给 **20 人以下创业团队的技术负责人**用，核心是把散落的群聊消息汇总成周报草稿。需要登录、要长期存数据，技术栈 React + FastAPI + PostgreSQL，全新项目。
>
> **我的判断**：这个产品真正难的地方不是「生成周报」——那个调一次模型就有了——而是**群聊消息怎么合法地拿到**。企业微信的会话存档接口要单独申请权限，而且客户未必开。如果你指望用户手动导出聊天记录再上传，产品价值会掉一大半。
>
> 所以我打算重点问三件事：① 消息从哪来 ② 周报长什么样才算合格 ③ 谁有权看谁的周报。**方向不对的话现在就打断我。**」

- **双向体现**：不是「请补充你的需求」，而是先给出判断和风险，甚至指出用户可能没意识到的阻塞点。
- **退出判据**：用户确认，或用户修正后 AI 复述一遍新的理解。

---

### S1 场景落地

- **核心任务**：拿到**一条完整动线**，细到「打开工具 → 点什么 → 等多久 → 拿到什么 → 做什么」。
- **话题**：真实使用过程。
- **产出**：主场景动线（写入已知信息，供 PRD 第 3 章与提示词套件的用例使用）。

**话术示例**

> 「先走一遍完整场景。我按最常见的情况假设一条动线，你直接改我：
>
> **周一早上，负责人打开工具 → 选一个群 + 选时间范围（默认最近 7 天）→ 点生成 → 等 30 秒 → 拿到一份按人分组的草稿 → 手动改两处 → 复制到飞书群。**
>
> 需要你确认两点：
> 1. 这个动线对吗？还是你想要的其实是**每周五自动推送到群里**、人根本不用打开工具？后者要做定时任务和机器人，工作量翻倍。
> 2. 「按人分组」是我加的——你的场景里，周报应该按人分还是按项目分？」

- **双向体现**：AI 自己造了一条默认动线让用户改，而不是让用户凭空描述流程。
- **退出判据**：存在一条完整动线，且用户认可它是主要场景（次要场景可留到 S2）。
- **跳过代价**：跳过会导致 PRD 第 3 章写不实、提示词套件缺用例，所以 S1 建议不跳过。

---

### S2 功能细化（**主要战场，可能占 2 轮**）

- **核心任务**：把 `core_features` 里每条一句话，展开成**含描述 / 输入 / 输出 / 边界条件**的条目——这正是 PRD 第 4 章的硬要求。
- **话题**：一次聚焦 1–2 个功能，问最影响实现的那几处。
- **产出**：功能条目（结构化，含输入 / 输出 / 边界 / 异常），供 PRD 第 4、6 章与接口文档使用。

**话术示例**

> 「功能 1「自动汇总群聊消息」我要问细一点，因为接口文档和实现提示词都得靠这些细节。
>
> **我的建议**是：按时间窗口拉取（默认最近 7 天）、按人聚合、**过滤掉闲聊**（少于 5 个字或纯表情的消息直接丢）。理由是周报关心进展，而群聊里 70% 是「收到」「哈哈」这类噪音，全量喂给模型既费 token 又干扰判断。
>
> 想确认：
> 1. 「闲聊」这个过滤规则你认可吗？还是宁可全量喂给模型让它自己判断？（**建议：按规则过滤**，成本可控且行为可预测）
> 2. 如果某个人这周一句话都没说，周报里是**不出现他**，还是写「本周无进展」？（**建议：不出现**，避免周报变长）
> 3. 消息拉取失败时（授权过期 / 接口限流），是整体失败还是**跳过该群继续生成**？（**建议：跳过并提示**，部分成功好过整体失败）」

- **双向体现**：三个问题各自挂了建议答案和理由，用户可以直接采纳；同时 AI 主动引入了用户没想到的边界情况（第 3 问）。
- **退出判据**：每个 P0 功能都有输入、输出、至少一条边界条件。
- **收尾话术**（转入 S3 时）：「功能细节够了。接下来我要**砍一些东西**，因为按现在这个范围做不完。」

---

### S3 边界与优先级

- **核心任务**：明确**不做什么**，并给功能分级（PRD 第 4 章要求 P0/P1/P2）。
- **话题**：范围、取舍、优先级。
- **产出**：范围清单（做 / 不做）+ 每个功能的优先级。

**话术示例**

> 「范围上我建议**砍掉两件事**：
> - **不做跨群汇总**——复杂度翻倍，但你的用户一个团队通常就一两个活跃群，价值有限。
> - **不做实时**——周报是按周看的，按天同步完全够用，实时会让架构复杂一个量级。
>
> 砍掉这两个，首版大概 3 周能出来；不砍的话，光群聊授权和去重就要多花两周。
>
> 我列个候选，你挑「这版一定要有」和「这版绝对不做」：
> 多群汇总 / 定时自动生成 / 周报模板自定义 / 历史周报检索 / 导出到飞书
>
> 另外提醒一句：`page_count` 你填的是 **2–3 个页面**，但上面这些如果都要，页面会涨到 6 个以上。**你是想压范围，还是想改页面数？**」

- **双向体现**：AI 主动建议砍需求并给出工期代价；同时用表单里 `page_count` 的数据反向质疑范围——这是双向对话才有的交叉检查。
- **退出判据**：有明确的「不做清单」，且 P0 功能数量收敛到可交付（建议 ≤ 5 条）。

---

### S4 约束与验收（**条件触发**）

- **核心任务**：补齐表单里留空的关键维度，并拿到「什么算做对了」的可测试口径。
- **触发条件**：`success_metrics` / `compliance` / `hard_constraints` / `scale_expectation` **任一为空**。全都填了就直接跳过本阶段。
- **产出**：成功指标、非功能约束、验收口径。

**话术示例**

> 「你的表单里**成功指标**和**安全合规**都空着，这两个空白会直接变成 PRD 里两章空话，所以我给你补默认值，你只判断对不对：
>
> - **成功指标**：上线 1 个月内 **10 个团队周活**，单次周报整理耗时从 2 小时降到 **10 分钟以内**。选这两个数是因为它们分别对应「有人用」和「真的省时间」，比「提升效率」这种话可测。
> - **合规**：群聊内容属于公司内部信息，建议**不外发、不出境、保留操作日志**。如果你们已经在用企业微信，这些要求其实本来就受企业微信的合规约束，等于白拿。
> - **验收口径**：我认为「生成合格」的最低标准是——**草稿里 80% 的内容不需要修改**。你认可这个门槛吗？还是你的标准更低/更高？」
>
> 「这些都可以之后在文档里改，但**现在定一个数**，PRD 的第 2 章和第 6 章才写得实。」

- **双向体现**：AI 主动给数值和理由，用户只做判断；并且解释了「为什么这么选」而不是拍脑袋。
- **退出判据**：成功指标有可量化的值；非功能约束有至少一条；验收口径明确。

---

### S5 摘要确认（交接生成）

- **核心任务**：汇总信息，让用户确认，然后触发生成（F3.9 + F3.10）。
- **关键设计**：摘要**必须三分类**，让用户一眼看出哪些是事实、哪些是 AI 的假设、哪些还没定。

**话术示例**

> 「信息够了，我汇总一遍。**三类要分清**：
>
> **① 你明确说的**（8 条）
> - 目标用户：20 人以下创业团队的技术负责人
> - 平台：Web 网站，需要登录（企业微信）
> - 核心功能：汇总群聊、按人生成草稿、可编辑导出 —— 导出只做 Markdown 和飞书
> - 不做：跨群汇总、实时同步
>
> **② 我替你定的**（3 条，你可以改）
> - 闲聊过滤：少于 5 字或纯表情的消息不进周报
> - 拉取失败时跳过该群继续生成，不整体失败
> - 成功指标：上线 1 个月 10 个团队周活
>
> **③ 还没定的**（2 条，会写进 PRD 第 8 章「开放问题」）
> - 企业微信会话存档权限能否申请下来（**这条不解决，产品可能做不成**）
> - 历史周报要不要保留、保留多久
>
> 确认没问题的话我就开始生成，顺序是 **PRD → 接口文档 → 提示词套件**，大约 3 分钟。中间可以取消。」

- **双向体现**：「我替你定的」这一类是双向模式的直接产物，用户不需要逐条回答，只需扫一眼有没有明显错的。
- **退出判据**：用户确认 → 进入生成（F3.10）。
- **注意**：生成不该自动开始。三份文档串行最坏约 4 分钟且有真实成本，误触发代价大（F3.10 的建议结论）。

## 5. 阶段过渡规则

### 5.1 正常过渡

AI 在切换阶段时用**一句话说明为什么换话题**，不静默切换：

> 「功能细节够了，接下来我要砍一些东西。」（S2 → S3）
> 「范围定了。最后补两个空着的项。」（S3 → S4）

### 5.2 条件跳过

| 阶段 | 跳过条件 |
| --- | --- |
| S4 | 四个约束字段全部非空，**且** `need_auth` / `core_entities` / `style_preference` / `need_database` / `integrations` / `existing_system` / `product_type` 中没有「填了但很粗」的答案 |
| S2 的第二轮 | 所有 P0 功能已有输入 / 输出 / 边界 |
| S1、S3 | **不建议跳过**。这两阶段分别决定产物写不写得实、范围收不收得住 |

跳过必须在摘要里体现为「**这项表单已提供，未重复确认**」，让用户知道 AI 没漏，只是没问。

### 5.3 用户主动干预

用户在任何阶段都可以：

| 用户行为 | 系统响应 |
| --- | --- |
| 说「够了，直接生成」 | 立即进 S5 摘要确认（F3.4「用户手动结束」） |
| 说「跳过这个」 | 该项标 `[待确认]`，进 PRD 第 8 章（F3.6） |
| 说「回到前面那个问题」 | 回到该阶段，答案覆盖旧值（F3.15） |
| 说「我不懂，你定吧」 | AI 采纳自己的建议值，并在摘要里归入「**我替你定的**」 |
| 打断当前问题问别的 | 先回答，再问「要不要继续刚才那个问题」 |

「我不懂，你定吧」这一路是双向模式必须支持的——目标用户是产品经理，不可能所有技术细节都有判断力。

### 5.4 强制收敛（轮次上限）

到第 4 个提问轮次仍未收敛时，AI **停止追问**，把剩余未决项按默认值处理，直接进 S5：

> 「我们聊了 4 轮，还有 2 项没定。我按常规做法定了默认值（列在「我替你定的」里），另外 1 项实在没法替你定，会写进开放问题。你也可以等文档出来直接改。」

这是 F3.5 的落地：**没有上限，对话会变成无限打磨，而用户要的是 10 分钟拿到文档。**

### 5.5 冲突处理（F3.11）

任何阶段发现新答案与已有信息矛盾时：

1. **立即显式指出**，不继续往下问；
2. 说清矛盾点和后果；
3. 给出建议（通常是「以新答案为准 + 说明为什么」）；
4. 用户确认后更新，并在摘要里标注「**此处与表单原答案不同**」。

## 6. 对现有实现的影响

### 6.1 提示词已按阶段拆好

`core/prompts/` 下的文件：

| 文件 | 作用 |
| --- | --- |
| `clarify_common.md` | 角色基线、**引导技巧清单（A–D 正向 / E 反模式，共 26 条）**、JSON 输出格式契约、硬性禁令、占位符清单 |
| `clarify_s0.md` | S0 开场复盘 |
| `clarify_s1.md` | S1 场景落地 |
| `clarify_s2.md` | S2 功能细化 |
| `clarify_s3.md` | S3 边界与优先级 |
| `clarify_s4.md` | S4 约束与验收 |
| `clarify_s5.md` | S5 摘要确认 |

system prompt = `clarify_common.md` + `clarify_s{阶段号}.md`，顺序不可颠倒。

**渲染方式必须是 `str.replace` 或 `string.Template`，绝对不能用 `str.format()`。**
提示词里既有 `{form_summary}` 这类占位符，也有输出格式示例里的 JSON 花括号，
`str.format()` 会把 JSON 内容当成占位符名 —— 实测报错为 `KeyError: '\n  "message"'`。

旧的 `clarify.md`（一次性输出问题清单 + `ENOUGH` 哨兵）**已被这 7 个文件完全取代**，
它没有阶段概念、给不出建议、也承载不了四段结构，重构时应直接删除，
而不是留作降级路径 —— 留着它就意味着两套澄清逻辑长期并存。

### 6.2 `ClarifyResponse` 必须扩展

双向对话要求每轮的 AI 输出**同时含文本和结构化问题**。响应模型至少要能承载：

| 字段 | 用途 |
| --- | --- |
| `message` | 正文（含【我的判断】【依据】），Markdown 渲染 |
| `questions[].question` | 问题文案 |
| `questions[].suggested_answer` | **建议答案**，前端渲染成「采纳」按钮 |
| `questions[].reason` | 建议理由 |
| `conflicts[]` | 发现的矛盾，需要高亮提示用户 |
| `stage_status` | `asking` / `done`，驱动服务端状态机推进 |
| `open_questions[]` | 本轮跳过的项，累积成 PRD 第 8 章 |

现有的 `ClarifyResponse`（只有 `questions: list[str]` 和 `enough: bool`）承载不了其中任何一项。

**「一键采纳建议」必须做成一等公民。** 这不是交互优化，而是双向模式能压缩时间的前提：
用户只需判断，不需要从零描述。如果只是让模型"说话客气一点"而前端不给采纳按钮，
用户还是得逐条打字，「10 分钟拿到文档」这个目标就不成立。

### 6.3 Q2 实际上被这份设计定了

`docs/功能清单.md` 的 Q2 问的是「一次抛 5 问还是一次一问」。本设计选了**中间路线：每轮 1–3 问，每问带建议**。

理由：双向模式下每个问题都附带判断、依据和建议，认知成本远高于单向提问。一次抛 5 个重型问题，用户会跳过大部分，反而丢信息。**这也意味着 F3.1 的「最多 5 问」需要下调为「每轮最多 3 问」**（总量仍受 F3.5 的轮次上限约束）。

### 6.4 引导技巧清单（26 条，已并入共同文件）

技巧清单放在 `clarify_common.md`，每个阶段都注入，因为它跨阶段通用。

| 类别 | 条数 | 内容 |
| --- | --- | --- |
| **A 提问方式** | 5 | 先给判断再问 / 每问必带建议 / 优先封闭式问题 / 一轮最多 3 问且每问只问一件事 / 用具体默认值锚定 |
| **B 信息质量** | 5 | 主动补边界（空数据·失败·超量·权限·重复·撤销）/ 指标可量化 / 用代价说话 / 交叉检查已有信息 / 每个问题都要有归宿 |
| **C 表达方式** | 5 | 用用户的词 / 复述确认而非让用户重复 / 复述逐条可追溯 / 标注信息来源 / 承认不确定 |
| **D 节奏控制** | 5 | 收敛优先于完整 / 到轮次上限就停 / 给「跳过」留出口 / 尊重「我不懂你定吧」/ 发现矛盾立即停 |
| **E 反模式** | 6 | 原样抛回问题 / 一轮抛 5 个重型问题 / 只复述不给判断 / 用「提升体验」收尾 / 把「我替你定的」写成「你明确说的」/ 为问全而多耗一轮 |

**为什么把技巧和禁令分成两个区块**：它们的违反后果不同，混在一起会削弱各自的作用。

| 区块 | 性质 | 违反后果 |
| --- | --- | --- |
| 引导技巧 A–D | 正向手法，鼓励做到 | 质量下降 |
| 反模式 E | 反面清单，明确别做 | 用户明显不满 |
| 硬性禁令 | 硬约束，可直接校验 | 输出不可用（格式错、问到已答内容） |

**不要往「硬性禁令」里堆正向手法。** 禁令清单越长，模型越保守 —— 会倾向于少问、少说、少给建议，
恰好把双向对话的核心（A1 先给判断、A2 每问必带建议）压掉。
