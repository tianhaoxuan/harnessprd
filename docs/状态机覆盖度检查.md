# 状态机覆盖度检查报告

> 版本 v0.1 ｜ 检查对象：`docs/状态机设计.md`（13 状态 / 40 转换）× `docs/功能清单.md`（65 项）
> × `docs/状态数据设计.md`、`docs/会话持久化方案.md`

## 1. 检查方法

| 方向 | 方法 |
| --- | --- |
| **降级覆盖** | 枚举所有「进行中」情形，逐个检查状态机是否有中断后的兜底路径 |
| **入口出口** | 对 13 个状态逐个统计入边 / 出边，检查语义是否唯一清晰 |
| **状态遗漏** | 把功能清单里所有"会改变会话处境"的功能点，逐个找它对应的状态或转换 |
| **逐项对照** | 65 项功能清单 × 状态机是否有归属 |
| **关键词取证** | 用关键词检索交叉验证，避免凭印象判断 |

## 3. 「生成中」降级覆盖检查（重点）

系统里有**四类**「进行中」情形，不是一个：

| # | 进行中情形 | 状态表达 | 中断/孤儿后是否覆盖 |
| --- | --- | --- | --- |
| 1 | PRD 生成中 | `prd_generating` + `active_generation` | ⚠️ **部分**：有 `failed` 转换，但触发条件不含"任务消失" |
| 2 | 接口文档生成中 | `api_generating` + `active_generation` | ⚠️ 同上 |
| 3 | 提示词套件生成中 | `prompts_generating` + `active_generation` | ⚠️ 同上 |
| 4 | **对话轮次的 AI 回复中** | `dialogue` + `active_turn` | ❌ **完全没有** |
| 5 | 表单防抖保存（在途的 PUT） | 无 | ✅ 无需降级（幂等写，失败重发即可） |

### 3.1 三类文档生成的缺口

转换表里写的是：

> `prd_generating` | `failed` | `generation_failed` | **LLM 超时 / 网络错误 / 鉴权失败 / 返回空内容**

这五种都是**"LLM 返回了错误"**。而孤儿态是**"任务根本没了"** —— 进程重启、发版、任务崩溃，
这时没有任何 LLM 返回，`failed` 事件永远不会被触发，用户**永远停在"生成中"**。

`docs/状态数据设计.md` §6.1 和 `docs/会话持久化方案.md` §7.4 都定义了孤儿检测规则，
但**状态机文档里没有这条转换**，三份文档对不上。

### 3.2 对话轮次的缺口（最严重）

`dialogue --reply--> dialogue` 的条件写的是"**且 LLM 调用成功**（超时 / 502 则停在原状态并提示，F3.13）"。

问题在于：

| 疑问 | 状态机是否回答 |
| --- | --- |
| 用户消息落库了没有？ | ❌ 没说 |
| AI 回复生成到一半刷新，会不会重复 append 用户消息？ | ❌ 没说 |
| 服务重启导致这一轮丢了，用户怎么办？ | ❌ 没说 |
| 用户怎么重试这一轮？ | ❌ 只说"提示"，没有重试路径 |

《会话持久化方案》§6 定义了完整规则（用户消息先落库、`active_turn` 标记、
最后一条是 user 且 `active_turn` 为空则重新生成），但**状态机文档对此零覆盖**。

**按状态机文档实现的结果**：对话中途重启，用户发的那句话和 AI 的回复双双消失，
或者更糟 —— 消息重复入库。

## 4. 状态入口 / 出口清晰度检查

13 个状态的入边、出边数量：

| 状态 | 入边 | 出边 | 入口语义是否唯一 |
| --- | --- | --- | --- |
| `created` | 1（初始） | 2 | ✅ |
| `form_editing` | **4** | 1 | ❌ **见下** |
| `dialogue` | 3 | 4 | ✅（首次提交 / 补充信息） |
| `dialogue_summary` | 2 | 4 | ✅ |
| `prd_generating` | 3 | 3 | ✅ |
| `prd_review` | 2 | 5 | ✅ |
| `api_generating` | 2 | 3 | ✅ |
| `api_review` | 2 | 5 | ✅ |
| `prompts_generating` | 2 | 3 | ✅ |
| `prompts_review` | 2 | 6 | ✅ |
| `completed` | 1 | 4 | ✅ |
| `generation_failed` | 3 | 7 | ✅ |
| `abandoned` | 12（通配） | 0 | ✅ |

### 4.1 `form_editing` 是唯一有问题的状态

它有 **4 个入口**：

1. `created` → 首次填写
2. `dialogue` → 回退改表单
3. `dialogue_summary` → 回退改表单
4. `prd_review` → 回退改表单（作废全部下游）

但**出口只有 1 个**：`form_editing --submit_form--> dialogue`。

于是产生一个状态机回答不了的问题：

> **从 `prd_review` 回退改完表单、重新提交后，`dialogue.stage` 停在哪？**

- 若 `stage` 还停在 S4（对话已走完），`submit_form` 后 AI 会**认为没什么可问的**，直接进 `dialogue_summary`
- 若重置为 S0，用户之前 3–5 轮的对话内容是否白费？

**当前文档对这个问题零覆盖**，而这是一定会发生的路径（改表单是 F2.5 明确的 P1 功能）。

### 4.2 其余状态清晰

除 `form_editing` 外，13 个状态的入口出口都是唯一的、语义可判定的。
`abandoned` 有 12 条入边是通配写法，语义清晰（任何非废弃状态均可放弃）。

## 5. 是否遗漏状态

逐个考察候选：

| 候选状态 | 是否需要 | 结论 |
| --- | --- | --- |
| `deleted`（已删除） | ❌ 不需要独立状态 | F1.4 的「删除会话」是**数据删除**（`store.delete()`），不是状态转换。但需要澄清它与 `abandoned` 的区别（见 §7.4） |
| 对话轮次失败态 | ❌ 不需要独立状态 | 单轮 ≤15s，用户重发即可，不值得多一个状态。但**孤儿降级规则必须有**（见 §3.2） |
| 章节级重生成态 | ❌ 不需要独立状态 | 可复用 `{doc}_generating`，但需要 `active_generation.scope` 区分"整份 / 章节"（见 §7.5） |
| 过期/归档态 | ❌ 不需要 | 由 `reap` 直接删除，无需中间状态 |
| 暂停态 | ❌ 不需要 | 会话本来就允许长时间停留（`state_entered_at` 用于回收判定） |

**结论：没有遗漏的状态，但有两处"状态内的语义"没定义**（`form_editing` 多入口、`active_generation.scope`）。

## 7. 缺口清单与处理

### 🔴 G1 对话轮次的降级（最严重）

**处理**：状态机文档新增 §3.6「降级处理」，把四类"进行中"并列，明确：

| 进行中情形 | 中断/孤儿后的降级 |
| --- | --- |
| 文档生成 | → `generation_failed` + `last_error`，清空 `active_generation` |
| 对话轮次 | → **停在 `dialogue`**，清空 `active_turn` + 写 `last_error`；用户重发即重新生成该轮 |
| 表单保存 | 无需降级，重试即可 |

**为什么两者降级目标不同**：文档生成耗时（最坏 90s）且有成本，必须让用户显式决定是否重试 → 需要独立失败态；
对话单轮 ≤15s，重发一次即可，不值得多一个状态。

### 🔴 G2 孤儿生成态写进转换表

**处理**：三个 `*_generating --failed-->` 的触发条件补上「**或任务已消失（孤儿）**」。

### 🔴 G3 `form_editing` 多入口语义

**处理**：明确回退规则 —— 表单变了，对话结论可能失效，因此
**`stage` 重置为 S0、`round_index` 归零，`messages` 保留用于展示，
`known_info` 中来自表单的字段重算、来自对话的字段保留**，重新提交后重走对话。

### 🟡 G4 `abandoned` ≠ 删除

**处理**：澄清 `abandoned` 是状态机内的终态（会话仍存在，可被 `reap` 回收）；
F1.4 的删除是 `store.delete()` 数据操作，不进转换表。

### 🟡 G5 章节级重生成（F8.6）

**处理**：给 `active_generation` 加 `scope: "full" | "section"` 与 `section` 字段，
复用 `{doc}_generating`，不新增状态。

### 🟡 G6 版本回滚（F7.4）

**处理**：新增事件 `restore_revision`，从 `{doc}_review` 回滚到历史版本（自环）。

### 🟢 G7 三个轻微项

| 功能点 | 处理 |
| --- | --- |
| F1.6 会话自动命名 | 明确在 `submit_form` 转换中触发（此时才有足够信息） |
| F4.7 生成参数 | 归入 `dialogue_summary` 的可选操作，随 `confirm_generate` 一起提交 |
| F7.5 数据清理 | `reap` 是数据操作，不进转换表；但需明确它只回收 `created` / `abandoned` / `completed` |
