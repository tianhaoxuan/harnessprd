# 接口文档写作与可追溯规则

## 可追溯（F8.3）

- 每个接口都必须有 PRD 来源（`FR-xx`），且该编号必须真实存在于 `{prd_content}`
- 不允许凭空造接口 —— PRD 里没有对应功能需求的接口就是多余的
- PRD 第 2 章 MVP 表的每条 P0 功能需求都应至少对应一个接口

## 完整性（F8.5）

- 每个接口的错误响应要覆盖适用类别：参数校验失败、未登录、无权限、资源不存在、状态冲突、并发冲突、外部依赖失败
- 字段级细节必须补齐：类型 / 必填 / 唯一 / 默认值 / 索引
- 枚举值必须穷举，不能用「等」字收尾

## 覆盖必须双向闭合（F8.3）

第 6 章必须同时输出两张表：

| 表 | 内容 |
| --- | --- |
| 接口清单 | 每条接口 + 对应 `FR-xx` |
| 无接口功能 | `FR-xx` + 为什么不需要接口（如「浏览器本地暂存，无服务端交互」） |

判定规则：PRD 第 2 章 MVP 表里的每条 P0 功能需求，必须要么出现在接口清单里，要么出现在无接口功能表里；两边都不出现的才是真漏项。不许为了凑覆盖而造接口。

互斥规则：每条 `FR-xx` 只能出现在两张表之一（需要服务端接口 → 接口清单；完全不需要 → 无接口功能表）。不允许一条 FR 同时出现在两张表里；即使功能整体需要接口、只有某个子能力不需要，也整条归入接口清单，并在接口详情的「业务规则」里说明该子能力由前端承担。实测反例：一条 FR 同时进了两张表（撤销只是子行为，不是该 FR 整体）。

## 命名与格式

- 字段名、实体名、枚举值必须与 `{prd_content}` 逐字一致
- URL 命名：名词复数、kebab-case、层级 ≤ 2 层；动作型操作用 `POST /weekly-reports/rpt_001/publish` 这类形式
- 全文 JSON 字段命名风格统一，不得混用 `camelCase` 与 `snake_case`
- 400 = 请求本身不合法；422 = 请求合法但业务校验不过

## 示例质量

- 每个 JSON 示例必须可直接粘贴使用，不含 `xxx`、`...`、`<占位符>`
- 示例的值要符合字段的类型与约束（时间字段给合法 ISO 8601 串）

## 服务端范围（`platform`）

| `platform` | 服务端范围 |
| --- | --- |
| Web 网站 / 移动 App / 微信小程序 / 桌面应用 | 需要服务端，接口文档完整输出 |
| 浏览器插件 | 可能只需少量接口；纯本地运行时第 4、7 章可整章省略，并在第 2 章注明 |
| 后端服务 / 开放 API | 服务端即产品本身，接口文档是主要交付物 |

## 非 RESTful 分支

`api_convention` 指定其他风格时替换 URL 与请求响应形态；分页、时间、金额、空值等约定仍然适用。

| 取值 | 替换方式 |
| --- | --- |
| GraphQL | 单一入口 `POST /api/v1/graphql`；错误放 `errors[].extensions.code`，HTTP 一律 200 |
| gRPC / RPC | 方法名 `Service.Method`；用 protobuf 定义；无 URL 概念 |

## 接口排列顺序

按资源分组，组内按方法顺序 GET → POST → PUT → PATCH → DELETE；每个接口标注 `PRD 来源`。

## 输出格式

- 单一 Markdown 文档，章节标题用 `## 第 N 章 章节名`
- 每个接口用 `### <方法> <路径>` 作为标题
- 请求 / 响应示例放在语言标注为 `json` 的代码块里
- 字段表用 Markdown 表格，一行一字段
- 不输出目录
- 只输出 `{generate_scope}` 指定的章节或接口
