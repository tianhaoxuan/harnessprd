# PRD 生成工作流

把输入（表单字段 + 对话确认的信息）写成一份 PRD。四个步骤，顺序不要变：

校验输入 → 归一化需求 → 按模板渲染章节 → 生成后质量检查。

本文件只说做什么、按什么顺序做。**具体的写作规则、章节内容和输入约束都不在这里重复**，
以 `references/` 下那三份为准。顺序以本文件为准，规则细节以那三份为准。

## 先读参考文件

不要凭记忆写。每一步开始前读对应的文件：

| 文件 | 提供什么 | 哪一步用 |
| --- | --- | --- |
| `references/field-schema.json` | 输入契约：8 个字段、类型、枚举、5 个必填项 | 第 1 步 |
| `references/prd-template.md` | 6 章结构、每章必含子项与格式、字段到章节的对应 | 第 2、3 步 |
| `references/writing-rules.md` | 表达与禁止规则：结构化表达、去重、事实与建议、缺失处理、禁止编造、编号与追溯 | 全程 |

## 第 1 步 校验输入

用 `field-schema.json` 逐项核对，不要只看字段名在不在：

- 5 个必填项是否都有值，且不是空字符串
- 类型是否正确（`target_users` 允许字符串或字符串数组；`mvp_features` 是数组且至少一项）
- 带枚举的字段取值是否在允许集合内
- 数组元素是对象时，`name` 是否都有

三种结果分开处理：

| 情况 | 处理 |
| --- | --- |
| 必填项缺失或为空 | **停止生成**，指出缺哪几个字段。这是唯一需要停下来的时候 |
| 类型或枚举不对 | 停止生成，指出字段名、实际值、允许值 |
| 可选字段缺失 | 不阻塞，继续。但要记下哪些章节会因此变薄 |

校验通过后，先在内部列一份输入摘要：必填项齐了、可选字段给了哪几个、预计哪些位置要标 `[待确认]`。
这份摘要不输出给用户，只用来核对第 2 步的归一化结果。

不要替用户补缺失的必填项，也不要在文档里反问用户。

## 第 2 步 归一化需求

目的是把散落的输入整理成"按章可写"的结构。这一步不改含义，只做归类与取舍。
五件事：

1. **分配落点**：每个信息点归到一个章节，按 `prd-template.md` 的「字段与章节的对应」执行。
   `technical_constraints` 会拆到两章（技术规格、非功能需求），拆的时候同一件事不要两边都详述。
2. **去重**：同一个功能或约束只保留一处详述，其余地方只列名称。判断归属与处理方式见
   `writing-rules.md` 第二节。
3. **区分事实与建议**：来自输入的信息记为事实；输入没有但该处必须有内容时记为建议，
   并在写的时候按 `writing-rules.md` 第三节的方式标注。
4. **列缺口清单**：逐章列出缺什么，并决定这一处走哪种处理（省略、写"本次无该维度输入"、
   还是就地标 `[待确认]`）。三档的选择标准见 `writing-rules.md` 第四节。
5. **分配编号**：给 MVP 功能定 `FR-xx`、给验收标准定 `AC-xx`，并记下每条 `AC-xx` 覆盖哪个
   `FR-xx`。编号在下游要用（接口文档按 `FR-xx` 列接口、套件按它做覆盖矩阵），所以在这一步
   一次定好、之后不再改。规则见 `writing-rules.md` 第六节。

归一化的结果是一份内部草稿，不输出。它决定第 3 步每一章写什么。

## 第 3 步 按模板渲染章节

- 严格按 `prd-template.md` 的 6 章顺序与标题格式输出，不增章、不删章、不改标题
- 每章的必含子项与固定格式（哪几处用表格、列是什么）照模板执行，这里不重述
- 逐章写、逐章自查：写完一章就对着该章的要求核一遍，不要等全文写完才发现缺子项
- 缺口按第 2 步的清单处理，不要临时改成"编一段看起来相关的内容"
- 语言与结构规范按 `writing-rules.md` 执行

## 第 4 步 生成后质量检查

分两类。结构类可以逐条机械核对，内容类需要判断。

结构检查：

- 6 章齐、顺序正确、标题格式与模板一致
- 每章的必含子项都在；三处表格的列与模板一致（MVP 五列、验收标准三列、页面列表四列）
- 8 个输入字段都有落点，没有收了却没用上的字段
- 标题层级不超过三级；没有模板之外的章节，没有"备注""说明"这类附加小节
- 没有残留占位符（形如 `{字段名}` 的文本），没有把模板里的说明文字当成正文写进去

编号检查（机械核对，逐条数）：

- `FR-xx` 从 `01` 起连续、不重号，条数与 MVP 功能条数一致
- `AC-xx` 从 `01` 起连续；每条 MVP 功能至少被一条 `AC-xx` 覆盖
- 没有孤儿 `AC-xx`：每条验收标准的「对应功能」都能在 MVP 表里找到
- 第 3 章支撑功能、第 6 章在范围内引用的编号都真实存在

内容检查：

- 功能名在第 2、3、6 章逐字一致
- 每条 MVP 功能都有优先级和边界条件；若全部是 P0，要有理由或标注
- 非功能需求四类都出现，且带数字或阈值
- 技术规格的五个子块都在：认证与权限、数据与存储、前后端技术、部署方式、外部依赖。
  数据实体与外部依赖是接口文档的取数来源，只要输入里有就不能省
- 项目范围的两张表与第 2 章一致：「在范围内」覆盖全部 MVP 功能，「不在范围内」不为空
- 抽查业务规则、指标数值、安全合规、外部依赖、角色权限这几类，逐个确认能在输入里找到出处
- `[待确认]` 标在受影响的原地；模糊表述已清理

检查不合格就修完再输出，不要带病交付。若某一处反复不合格（例如输入确实不足，怎么写都不成立），
降级为 `[待确认]` 并如实写"本次无该维度输入"，不要硬写一段凑数。

## 边界情况

- **输入互相矛盾**（例如 `platform` 与 `technical_constraints.deployment` 说法冲突）：
  不要自行取舍。各自按事实写进对应章节，并在该处标 `[待确认]`。
- **可选字段一个都没给**：仍要产出完整的 6 章结构，缺口按缺失处理走，不要退化成半份文档。
- **输入很长**：正常处理，不要截断。整份 PRD 只有几千字符，一次生成就能出全，不需要分片。
- **同一字段里混了多个主题**（例如 `product_goal` 同时讲了问题和合规要求）：
  按主题拆到各自的章节，保持原文含义。

## 输出

只输出文档本身：从第一个标题开始，不加前缀、不加说明、不加总结。
格式细节见 `writing-rules.md` 第七节。
