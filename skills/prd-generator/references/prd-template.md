# PRD 模板

这份模板按使用方给定的 6 章结构写，字段定义见同目录的 `field-schema.json`。
**它就是本次要用的唯一结构**：产物是一份 6 章的 PRD，不增章、不减章。

产物是一份单一 Markdown 文档，直接从第一个标题开始。
要输出的章节是下面那 6 个（`## 1. 产品概述` 到 `## 6. 项目范围`）。

## 使用说明

本节是模板自身的说明，不要出现在产物里。

### 章节结构

| # | 章节 | 是否必出 | 输入来源 |
| --- | --- | --- | --- |
| 1 | 产品概述 | 必出 | `product_name`、`product_goal`、`target_users`、`platform` |
| 2 | 功能需求 | 必出 | `mvp_features`、`v2_features`；验收口径可来自对话确认的信息 |
| 3 | 页面设计 | 必出 | `ui_pages`，缺失时由功能反推 |
| 4 | 技术规格 | 必出 | `technical_constraints` 的 `stack`、`deployment`，以及认证 / 存储 / 权限 / 依赖类信息 |
| 5 | 非功能需求 | 必出 | `technical_constraints` 的 `performance`、`compliance` |
| 6 | 项目范围 | 必出 | `mvp_features` 与 `v2_features` 的差集 |

标题格式用 `## 1. 产品概述` 这样的一级章节加序号，子块用 `###`，最多到三级标题，不输出目录。

### 编号与追溯

第 2 章有两套编号，它们是**下游文档的取数依据**，不是装饰：

| 编号 | 含义 | 谁在用 |
| --- | --- | --- |
| `FR-01`、`FR-02`…… | 一条 MVP 功能 | 接口文档按它列出「每个接口对应哪个功能」，并核对有没有功能没接口；提示词套件按它做覆盖矩阵 |
| `AC-01`、`AC-02`…… | 一条验收标准 | 提示词套件的测试类步骤按它写用例 |

规则（详细要求见 `writing-rules.md` 第六节）：

- 两套编号都从 `01` 起**连续**编号，不跳号、不重号、不用 `FR-1` 这种写法
- 编号只给 MVP 功能。未来功能不编号，也不写验收标准
- 下游文档要求「每条功能都能被追溯到」，所以 MVP 功能一条都不能漏编号


### 字段与章节的对应

八个输入字段都必须有落点，不能有字段收下却没用上：

| 输入字段 | 落在 |
| --- | --- |
| `product_name` | 第 1 章 |
| `product_goal` | 第 1 章的核心问题，以及全文的目标口径 |
| `target_users` | 第 1 章 |
| `platform` | 第 1 章，并影响第 4 章部署方式与第 5 章兼容性 |
| `mvp_features` | 第 2 章 MVP 表格与验收标准、第 3 章的支撑功能、第 6 章在范围内 |
| `v2_features` | 第 2 章未来功能、第 6 章不在范围内 |
| `ui_pages` | 第 3 章 |
| `technical_constraints` | 第 4 章全部（认证与权限、数据与存储、技术、部署、外部依赖），第 5 章的性能与安全 |

### 输出格式

- 单一 Markdown 文档，不要用代码块包裹整篇，不要在文档前后加解释性文字
- 直接从第一个标题开始，不要写「好的，我来生成」
- 结构化内容用 Markdown 表格
- 标题层级最多到 `###`
- 术语一致：同一概念全文只用一种叫法，功能名在三处（MVP 表格、页面设计、项目范围）逐字一致
- 受影响但不确定的位置就地标 `[待确认]`（这份模板没有单独的开放问题章节，就标在原地）

## 1. 产品概述

四项内容一项不能少：产品名称、核心问题、目标用户、平台。

- 产品名称：与 `product_name` 逐字一致，全文只用这一个叫法
- 核心问题：写现状与痛点，以及期望达到的效果。不要只写目标，缺了现状读者无法判断这件事值不值得做
- 目标用户：单个角色写一行，多个角色分条列。不要写「所有人」
- 平台：与 `platform` 一致，并说明该形态带来的约束（例如小程序要处理登录态，浏览器插件要处理权限申请）

建议用两列表（项目 / 内容）。核心问题超过三句时改为一段话，不要拆成子节。

## 2. 功能需求

分成三个子块，顺序固定。

### MVP 功能

用表格，列固定为五列：编号 / 功能 / 说明 / 优先级 / 边界条件。

- 编号从 `FR-01` 起按本表顺序连续编号，不跳号、不重号
- 一行一个功能，功能名与 `mvp_features` 里的名称一致
- 说明写「做什么」，以及关键的输入与输出，不写实现方式
- 优先级取 P0、P1、P2；`mvp_features` 里没给优先级时按 P0
- 边界条件写异常与极限情况，要具体到可判定，例如「时间跨度超过 31 天时返回 422」，
  不要写「处理异常情况」。确实想不到的写「暂无」，不要留空

### 验收标准

用表格，列固定为三列：编号 / 对应功能 / 验收标准。

- 编号从 `AC-01` 起连续编号。它与 `FR-xx` 是两套独立编号，不要写成 `FR-01-AC-01`
- 每条 MVP 功能**至少一条**验收标准，`对应功能` 列写它覆盖的 `FR-xx`；
  多条时填多个编号，用顿号分隔
- 验收标准要能执行、能判定通过与否，写成「给定……当……则……」或等价的明确条件。
  不要写「功能正常」「体验良好」「符合预期」
- 输入里给过验收口径时必须落在这里（例如「生成草稿中 80% 的内容不需要修改」），
  不要把它挪到第 5 章当指标写
- 验收标准只覆盖 MVP 功能。未来功能不写验收标准

### 未来功能

项目符号列表，每条一句话，来自 `v2_features`。未来功能**不编号**。
没有给 `v2_features` 时保留标题并写「暂无规划中的后续功能」。

## 3. 页面设计

三个子块：

1. 页面列表：表格，列是页面名 / 用途 / 路径 / 支撑功能，来自 `ui_pages`。
   `支撑功能` 列写该页面服务的 `FR-xx`（可多个，用顿号分隔），必须是第 2 章 MVP 表里
   已有的编号；一个页面服务全部功能时写「全部」
2. 模块划分：每个页面列出它包含的模块（区域或组件块），一句话说明各模块负责什么
3. 关键交互：每条写清触发条件与结果，例如「在编辑页点击保存且校验通过，写回草稿并提示已保存」。
   只写影响状态或数据的交互，不做交互细节的全量枚举

`ui_pages` 缺失时，由 MVP 功能反推页面，并在本章开头注明「页面清单由功能反推，待确认」。

## 4. 技术规格

五个子块，顺序固定。

- 认证与权限：认证方式 + 角色与可见范围。没有登录需求就明确写「无认证」，不要留空，
  也不要因为留空而塞一段不相关的权限内容进去。角色与可见范围只在输入给过角色信息时才写，
  写成「角色 / 可见范围」两列的小表；输入没给就写「本次无该维度输入，待补充」并标 `[待确认]`，
  不得自行设计角色体系
- 数据与存储：数据实体清单（实体名，以及实体之间的关系，一行一个）+ 持久化范围与大致数据量。
  没有持久化需求就写「无持久化」。**不写字段类型、长度、索引**，那些属于接口文档
- 前后端技术：来自 `technical_constraints.stack`。这是全文唯一允许写技术选型的地方
- 部署方式：来自 `technical_constraints.deployment`，写清环境（内网、私有云、公有云）与形态（容器、裸机）
- 外部依赖：用到的第三方服务、外部系统或对外接口。没有就写「无外部依赖」。
  **只写输入里出现过的**，不得因为常见就替项目补上（例如自作主张加短信、支付、地图服务）

数据实体与外部依赖这两项是**下游接口文档的取数来源**（接口的数据模型、外部依赖章），
所以只要输入里有就一定要写，不能省；输入里没有时按上面的方式标注缺失，不要省略子块。

输入里没给技术选型时，按平台形态给出建议并在前面注明「建议，待确认」，不要写成既定事实。

## 5. 非功能需求

四类，每类都要出现。要求是可判定的说法，带数字或阈值：

| 类别 | 要写什么 | 反例 |
| --- | --- | --- |
| 性能 | 响应时间、并发量、数据量级 | 要快、要流畅 |
| 安全 | 鉴权、数据保护、审计 | 要安全 |
| 可用性 | 可用时间、错误恢复、易用性要求 | 要好用 |
| 兼容性 | 端与浏览器、屏幕尺寸、离线要求 | 要兼容主流环境 |

某一类在输入里找不到出处时，写「本次无该维度输入，待补充」，并在该处标注 `[待确认]`。
不要用邻近内容顶替。

## 6. 项目范围

两张表：在范围内、不在范围内。

- 在范围内：用表格，列是编号 / 功能名，逐行对应第 2 章 MVP 表的 `FR-xx` 与功能名，
  两处逐字一致
- 不在范围内：这一张不能空。来自 `v2_features`，以及输入里明确说过不做的项。
  确实没有任何排除项时写「本期无明确排除项」并说明理由

范围这一章与第 2 章必须一致：第 2 章 MVP 表格里有的功能，这里都要出现（编号也一致）；
不在范围内的项不应出现在 MVP 表格里。
