# 提示词套件质量规则

## 覆盖完整（F8.4）

- `00-README.md` 必须含一张覆盖矩阵：PRD 功能需求 × 优先级 × 覆盖步骤
- PRD 里每条 P0 功能需求都必须至少被一步覆盖，否则就是实现漏项
- 步骤数量建议 5–12 步；P0 功能必须各占至少一步

## 依赖无环

- 步骤之间的「前置」关系必须构成有向无环图
- 不允许 A 依赖 B、B 又依赖 A
- 不允许某步引用编号更大的步骤作为前置

## 可判定

- 每条约束、每个验收点都必须能被一条命令或一次观察验证
- ❌「代码要优雅」「注意性能」「处理异常情况」
- ✅「禁止引入 ORM，统一用 `asyncpg` 裸 SQL」「时间跨度 > 31 天返回 422 + `RPT001`」

## 命名一致（F8.5）

- 实体名、字段名、接口路径必须与 `{api_content}` 逐字一致
- 术语必须与 PRD 附录 A 的术语表一致

## 无冗余

- 不重复粘贴整份 PRD，按需摘要引用
- 通用约束只写在类别 1；每步只写本步特有的
- 类别 5 不改写验收标准，原文照录

## 分支规则

按目标工具（Q5）：

| 取值 | 类别 1 的形态 |
| --- | --- |
| Cursor | 输出为 `.cursorrules` |
| Claude Code | 输出为 `CLAUDE.md` |
| Codex / 通用 / 未指定 | 输出为 `01-project-brief.md`，不使用任何工具专有语法 |

按项目类型（`existing_system`）：

| 取值 | 调整 |
| --- | --- |
| 全新项目 | 按默认流程 |
| 已有系统，要改造 | 类别 2 改为「现状梳理」（先读懂现有结构并输出报告，不建新骨架）；类别 4 每步必须增加「不要动哪些文件」 |
| 保留旧系统另建新的并对接 | 类别 3 增加「与旧库 / 旧接口的映射表」；类别 4 增加一个对接步骤 |
| 需要迁移历史数据 | 类别 3 增加「迁移脚本」子节，且必须含数据校验方式 |

改造型项目最容易出事的地方是 AI 不知道哪些文件「已有的、不要动」，会大范围重写，因此「本步不做」与「不要动」两节必填。

## 输出格式

本产物不是单一 Markdown 文档，而是多个文件，用文件分隔行切分：

```
=== FILE: 00-README.md ===
（文件内容）
=== FILE: 01-project-brief.md ===
（文件内容）
```

分隔行规则：

1. 分隔行独占一行，格式严格为 `=== FILE: <相对路径> ===`
2. 路径不含前导 `./`，不含 `prompt-suite/` 前缀
3. 每个文件一个块，顺序按编号
4. 文件内容里不得出现符合上述格式的行（否则会被解析器误判为分隔符）
5. 分隔行前后不加空行以外的任何文字

文件内容格式：

- 每个文件是纯 Markdown，不要再用代码块包裹整个文件
- 类别 4 的每步文件，小节标题固定为：`## 目标` / `## 前置` / `## 涉及文件` / `## 涉及接口` / `## 约束` / `## 验收` / `## 本步不做`
- 命令放语言标注为 `bash` 的代码块；代码用对应语言标注
- 文件路径用反引号包裹

只生成本次范围：

- 只输出 `{generate_scope}` 指定的文件
- 不要为未生成的文件留占位块
- `00-README.md` 的覆盖矩阵只列已生成的步骤；未生成的标为「（未生成）」并在文件末尾注明
